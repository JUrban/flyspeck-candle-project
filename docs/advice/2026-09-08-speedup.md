Plan: Avoid Unnecessary CakeML Bootstraps

The canonical CakeML bootstrap takes approximately 6–8 hours. It should run only when an input capable of changing the verified compiler binary has changed, or once for a formal release checkpoint. A repository commit change alone is not sufficient justification.

1. Define the compiler-input closure

Create a machine-readable manifest covering:

- compiler definitions and proofs;
- their transitive HOL dependencies;
- relevant build scripts and configuration;
- HOL and Poly/ML versions;
- target architecture and compiler flags.

Exclude non-compiler inputs such as:

- "candle/regression.py";
- Great100/Flyspeck scripts and expected results;
- reporting, comparison and orchestration code;
- documentation.

Hash this closure to obtain a "compiler_build_key".

2. Select the cheapest valid build mode

Reuse

If "compiler_build_key" is unchanged:

- verify the existing bootstrap receipt and binary hash;
- create a provenance transition binding that binary to the new test-runner revision;
- relink and run the affected tests;
- do not bootstrap again.

Incremental development build

If the closure changed but the affected theory subgraph is known:

- rebuild only that theory and its descendants;
- reuse independently validated predecessor artifacts;
- use the result for focused development testing, not final qualification.

Canonical build

Run a fresh cache-disabled bootstrap only when:

- the compiler-input closure changed and a release candidate is ready;
- the toolchain or build configuration changed; or
- the formal release procedure explicitly requires a fresh reconstruction.

One canonical binary can and should be used for both clean Great100 runs.

3. Make the decision fail-closed

Add automated tests proving that:

- changing "regression.py", reports or target corpora does not alter "compiler_build_key";
- changing compiler/proof sources, toolchain versions or flags does alter it;
- missing dependencies and source drift are rejected;
- reused artifacts pass the same independent binary/provenance verification as fresh artifacts.

Every report should state "FRESH", "REUSED" or "INCREMENTAL", together with the build key and binary hash.

4. Immediate application

Allow the current "5e6362f" canonical bootstrap to finish. Freeze and authenticate its resulting binary. Use that binary for:

- both final Great100 executions;
- runner-only corrections;
- cumulative Flyspeck work;

until the compiler-input closure genuinely changes.

If another runner or report defect is discovered, use the already-demonstrated schema-7-style transition instead of starting another eight-hour build.

5. Assurance boundary

Before relying on artifact reuse for formal S1 closure, document the compiler-input boundary and obtain the required independent approval. Until then, reuse it freely for diagnostic and focused testing, while retaining one fresh canonical build for final qualification.

This should reduce most compatibility iterations from eight hours to minutes or targeted-test time, while preserving the full clean bootstrap where it contributes actual assurance.
