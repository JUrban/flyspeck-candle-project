The clearest example of drift: checkpoint security

A small checkpoint/restart smoke test is appropriate now. The roadmap asks for checkpointing, stale-resume rejection and corruption tests. But the required model is much simpler: manifest-rooted paths, theorem-consistent boundaries, hashes, atomic checkpoint publication, and a resumed run yielding the same final fingerprint. It also explicitly requires relocation to a different absolute root. 

The worker has instead begun building something close to a hostile-host checkpoint security monitor.

That is not only premature; parts of the current provenance design are actually fighting the roadmap. One telling event in your trace was having to reconstruct a detached worktree at an exact historical absolute path because a terminal manifest pinned /project/worktrees/.... That is the opposite direction from the roadmap's relocation criterion.

Provenance should primarily bind:

commit → source hashes → compiler hash → configuration → theorem/state fingerprints

—not the historical pathname at which a worktree happened to exist.

I think the underlying conceptual mistake is this

The worker has blurred reproducibility with tamper-proof security against an active local adversary.

Those are different goals.

For this project, it is absolutely appropriate to defend against:

stale input, wrong commit, accidentally reused artifact, malformed certificate, skipped theorem, wrong binary, nondeterministic result, corrupted checkpoint.

But it is not necessary right now to build a security system robust against a malicious same-UID process racing pathnames, replacing helpers, escaping ptrace with CLONE_UNTRACED, manipulating mount namespaces, etc.

If the host kernel/user account is actively malicious, the attacker can attack the linker, the executable, the kernel, the filesystem, or the recorded output anyway. There is an unavoidable host TCB.

The roadmap understands this distinction. It says theorem authority comes from Candle kernel construction or explicit assumptions, while external parsers, shims, solvers and caches may be untrusted. 

That suggests the right design is:

> Don't prove that the orchestration system is impossible to tamper with.
Make the orchestration system logically untrusted, and make Candle/state fingerprints expose incorrect results.



The current fs-verity/ptrace/seccomp work may eventually be nice release hardening. It should not be consuming critical-path engineering before S1.
