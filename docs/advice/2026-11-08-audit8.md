Owner decision: G8 scope (2026-11-08)

Decision: one case-16594-only demonstrator build is authorised. It installs the payload-generic, program-fixed G5C callback, with the general proved evaluator as fallback for all other inputs. It is labelled as a demonstrator and an integration test of the whole runtime path. It does not complete the production architecture: replacing the case-specific dispatch with the plan-generic G5P callback is the next phase and will need a second build. Given the 3,450-6,800 CPU-hour stock envelope, the fast route is worth pursuing.

Preconditions, each recorded in the repo before the build starts:

1. Equation freeze. Freeze and hash the exact Candle-side equation set and call shape the callback recognises. Immediately before the build, export them afresh from the current Candle source and check a byte-for-byte match. Make no edits to those Candle definitions until G9 is done. This is the October drift lesson (v4.221).

2. Prepared state. Name the minimal predecessor state the case-16594 theorem needs. Rehearse and time its cold construction on the current binary, and record expected time and peak RSS.

3. Build preflight. Give the exact dependency cone, the stage list, and predicted elapsed time and peak RSS per stage, starting from Magnus's 8-10 h for a stock binary. Give a stop rule for each stage. No timeout increases on silence.

4. Integrated call check. Pass the exact call that Candle constructs, using the same construction code G9 will use and the padded payload, to the G6 binary, and confirm it returns Some.

5. Fallback regression. On the new binary, re-run one non-16594 stock record (e.g. 139514/3) through ordinary Kernel.compute and confirm the same original theorem, the same digest, and CPU time comparable to the current runtime. State which evaluator handles fallback calls (upstream exec or compute_pure_fast_eval), and confirm the stock-route benchmarks were measured through that same path.

Exit (G9): Kernel.compute takes the fast branch on the genuine call and the literal original case-16594 theorem results (digest 8bb2c1bf3d1c1944d497c0da68b88207, no assumptions, no axiom growth). Record prepared-state construction, Kernel.compute, handoff, reconstruction and peak RSS separately, and compare with the stock route's ~480 s post-restore on the same machine.

Stop rules: preserve and diagnose any failed build stage, and write a diagnosis before more than one retry. If the run misses the fast branch, stop and report the exact mismatch rather than patching around it.

In parallel, without delaying the build:

- the G5P discriminator (4 h plus the first-day semantic test);
- controlled timings for 161160/23, TSKAJXY/26 and one larger supported record;
- what the minimal NL prepared state would weigh, since 17 GiB per worker caps parallelism for both routes;
- a batch runner for the stock route, which either route will need. Run it only on capacity that does not slow the build.
