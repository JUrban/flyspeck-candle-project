# v1.3 top-level runtime frontier — 2026-08-27

## Result

The compatibility boundary immediately after the selected `#load` directives
is not just a missing `Format.std_formatter` value.  A scan of the 398-node
manifest-selected graph found a correctness-relevant dependency on OCaml's
top-level compiler interface.  A dummy `Toploop` module, a successful no-op
`Toploop.use_file`, or blanket directive erasure would make the loader advance
without checking the source that Flyspeck intended to execute and is therefore
not an admissible green result.

This is a G2 language/runtime and G6 loader discovery.  It is not S1, S2, or S3
acceptance evidence.  The governing Flyspeck source remains the unmodified
commit `1ce0353008eba83d3c76ae9a25c3c242e4802d53`.

## Selected interface inventory

The existing comment/string-aware scanner was run over the exact source-node
set in `candle/flyspeck_manifest.json`.  It found these qualified uses:

| Module | Selected executable occurrences | Members |
| --- | ---: | --- |
| `Toploop` | 19 | `execute_phrase` 5, `parse_toplevel_phrase` 5, `parse_use_file` 3, `getvalue` 2, `toplevel_env` 1, `use_file` 1, `use_silently` 1, constructor `String` 1 |
| `Lexing` | 5 | `from_string` 5 |
| `Obj` | 3 | `magic` 3 |
| `Format` | 106 | 29 members, mostly already supplied by Candle's pretty-printer compatibility layer |

The currently absent executable `Format` subset is nine occurrences:
`std_formatter` five times, `formatter_of_buffer` once, `pp_set_margin` once,
and `sprintf` twice.  Supplying those four names alone would make the source
typecheck further, but would not close the top-level evaluation dependency.

The source locations that establish the critical distinction are:

- `text_formalization/build/strictbuild.hl:90` calls
  `Toploop.use_file Format.std_formatter` from its dynamic loader;
- `jHOLLight/caml/ssreflect.hl:723-750` parses identifier assignments from
  strings and executes them to resolve theorem arguments used by tactics;
- `text_formalization/general/flyspeck_eval_4.14.hl:13-28` exposes general
  string evaluation (the source says it is not used by formalization files);
- `text_formalization/general/update_database_400.ml` executes constructed
  source strings, reads the OCaml top-level environment, casts values with
  `Obj.magic`, and rebuilds the theorem search database; and
- the selected `general/serialization.hl` loads the 4.x update-database branch
  and invokes `update_database` during theorem serialization.

The conservative source graph contains both `update_database_400.ml` and
`update_database_310.ml`, because both literal branches occur in
`serialization.hl`.  The pinned `Sys.ocaml_version = 4.14.1` execution route
selects `_400`; future manifest evidence must record this branch choice rather
than claiming that both files execute.

There is a second inventory issue: `update_database_400.ml` constructs source
programs inside strings and passes them to `Toploop.execute_phrase`.  A scanner
that deliberately masks string bodies is correct for ordinary qualified-name
scanning, but it is not a complete inventory of dynamically evaluated code.
Those payload constructors need their own explicit contract or removal by an
audited compatibility transformation.

## Architecture consequence

The roadmap's D1 requirement to enumerate source files in exact load order
supports a static, manifest-generated sequence of top-level `needs` directives.
That mechanism can remove `Toploop.use_file` from the *executed loader path*
without changing or pretending to execute the function: the original
strictbuild source is still parsed and typed, while the manifest owns the
actual ordered file loading.  The generated sequence must be hash-bound to
`Build.build_sequence_full`, reject reorder/corruption, and preserve the state
manager action at each declared boundary.  Until those gates exist,
`Toploop.use_file` remains open and must fail closed if called.

Static file enumeration does not solve `ssreflect` theorem lookup or
serialization's environment enumeration.  Those require one of two auditable
designs:

1. extend the verified CakeML REPL/compiler path with a typed dynamic-evaluation
   and environment-enumeration interface, including inference, namespace,
   state, rollback, and machine-code proof obligations; or
2. introduce a deterministic typed theorem registry and narrowly transform
   the selected compiler-internals-dependent source sites, proving that all
   identifier lookups and serialization inputs used by the S3 route agree with
   the reference OCaml run.

The second design is likely smaller, but it is not accepted merely on that
intuition.  The next runtime frontier must show which `ssreflect` lookups and
serialization operations actually execute, and the reference run must produce
the name/value evidence needed for an equivalence gate.  No dummy return,
unchecked external answer, generic `Obj.magic`, or silent skip is allowed.

## Next gates

1. Complete and integrate exact fail-closed `#load` recognition after the
   shared CakeML bootstrap releases its HOL build directory.
2. Add a manifest contract for the selected top-level/compiler modules,
   conditional branch choice, and dynamically evaluated string payloads.
3. Generate the exact top-level source sequence and test sequence/hash drift,
   while keeping accidental calls to `Toploop.use_file` fail-closed.
4. Run the compiled loader to localize the first active `Toploop`/`Format`
   failure rather than assuming all selected definitions execute.
5. Compare a typed theorem-registry design with a verified nested-evaluation
   design against the actual `ssreflect` and serialization call traces before
   selecting the remedy.
