## Revised amortization finding

The shared proof fragments and restored base inputs were byte-identical to
the preceding single-result lean run. Nevertheless, their late load took
1,862.198 seconds here versus 1,308.087 seconds in that run, an increase of
554.111 seconds or 42.36 percent. This is not explained by a source-set
difference. Retained-state garbage-collection or heap-traversal cost is a
plausible explanation, but has not been isolated; ordinary run variation is
not excluded.

For orientation only, the earlier proof-rich genuine prefix-16 phase cost
about 582.680 seconds per segment, while this varied lean batch averaged
300.829 seconds of recurring work. Charging the newly observed shared setup
against that approximate baseline moves the cold break-even from the earlier
provisional estimate of about four to **about seven comparable segments**.
The samples are different genuine subtrees, so this is a planning estimate,
not an apples-to-apples performance claim.

The main architectural conclusion remains positive: setup is demonstrably
shareable, compute cost varies meaningfully with authentic data, and retained
results do not increase sampled RSS at four segments. A larger genuine batch
or a whole-inequality run should now test whether the shared-load penalty
stays bounded before further micro-optimization.
