## Durable long-run hazard database

The new `docs/long-run-hazard-ledger.json` initially records 15 observed or
credible failure classes.  Each has a root cause, first evidence, enforcement
phase, and registered executable check.  The policy is:

- a run with a declared maximum over one hour requires a `status=0` receipt
  over the exact ledger and controller bytes;
- an unknown check blocks the run; and
- every newly observed failure must be added with a cheap discriminator before
  any retry.

The gate currently executes ten distinct checks: verified runtime provenance,
five clean pinned worktrees, normalization closure, literal source closure,
module/load-order closure, full checkpoint hashes, controller caps, exact fast
theorem/postcondition requirements, fresh run target, and live resource
headroom.

The first full gate test took 68.04 seconds, most of it hashing 9.8 GB of
checkpoints.  It correctly rejected the spent v664 controller because:

1. the module/load-order audit is not green;
2. v664 predates and therefore does not invoke the new mandatory gate; and
3. its output target already exists.

The test also exposed and fixed a self-detection bug in the resource check:
the gate's own launcher command mentioned the controller path and was initially
mistaken for an active duplicate.  The check now excludes the gate's process
ancestry; a focused regression returns zero active matching controllers.

## Next authorization boundary

No new long run may start until all of the following are true:

1. the complete prerequisite/module graph is explicit and topologically
   ordered;
2. every resulting source identity and hash is authenticated;
3. a focused parser/static preflight and, where necessary, a short restored
   availability probe pass;
4. a new controller names a fresh output directory, invokes the hazard gate,
   and retains phase-specific hard caps; and
5. the exact gate reports `status=0`.

Only then is one replay justified.  The intended caps remain 90 minutes for
base setup, 45 minutes for actions 0--49, two hours for support, and 30 minutes
for each of two exact theorem calls: 4h15m worst-case sequential, with a
measured expectation closer to 1.5--2 hours.  Every completed phase is saved,
and the run stops at the first error.  Another verified-compiler build is not
part of this plan.
