## Verdict

Production integration is rejected with no P0 and four P1 findings:

1. The plan's exact producer schema does not bind the request generator, its
   fixed-source loader, or its Python/runtime closure.  Request semantics are
   not otherwise independently rederived.  The migrated authority must add a
   closed generator record or make generation part of the one authenticated
   collector entrypoint.
2. Stock HOL Light computes an MD5 from one pathname open and later reopens the
   source for parsing.  The request maps that MD5/basename pair to a plan
   SHA-256 claim; it does not establish that the claimed bytes were parsed.
   The LP wrapper similarly deserializes a path first, then reports a
   basename-indexed planned SHA-256.  Immutable inputs must therefore cover the
   complete run: strictbuild, all 297 actions, all 39 LP inputs, final target,
   serializer, and authorized external tools.  Startup-only mediation is not
   sufficient.
3. The current child contract puts `request.ml` on stdin.  OCaml toplevel mode
   prints phrase results between the generator's separate semantic phrases,
   contradicting the parser's no-ordinary-output semantic tail.  The migrated
   invocation must use an authenticated immutable positional script (or an
   equivalently exact noninteractive wrapper), with stdin separately closed.
4. The parser treats an ordinary line beginning `exception` as a failure.
   Successful HOL/Flyspeck loads legitimately print declarations such as
   `exception Sanity` and `exception Unsolvable`.  Ordinary output must remain
   non-evidentiary, but only the reserved marker/PFT byte grammar, authenticated
   control flow, status and terminal record may decide acceptance; English-like
   prefixes cannot be generic failure evidence.

The previously found `hol.ml` contradiction also remains: `-init hol.ml` does
not put `hol.ml` into stock `loaded_files`.  The generator correctly does not
