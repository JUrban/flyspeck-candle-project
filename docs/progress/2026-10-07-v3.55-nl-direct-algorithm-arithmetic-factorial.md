## Question and controls

The broad performance investigation keeps two original observations separate:

1. about 15 times between the then-current exact-output native computation and
   its encoded `Kernel.compute` execution;
2. about 341 times between the original generic native fixed-scale equations
   and the historical specialized C++ verifier.

Those are starting diagnoses, not immutable ratios. Later untrusted native
prototypes have changed the numerical side substantially, while no new
reflected Candle measurement has yet changed the first ratio.

The present experiment implements the authenticated case-10173 top-level
formula as a direct primitive plan:

- the exact sum of its seven source constants;
- six source-derived coordinate-square-root terms;
- the source-derived coefficient on the historical dihedral primitive; and
- one final centered Taylor completion.

The plan validates the 54-instruction source shape, prepared source nodes,
coordinate coverage, root slots, dihedral chain, final add chain, and exact
coefficients before it runs. It does not accept an arbitrary formula under
the case-specific instruction. This remains an unproved native development
prototype.

Two controls make the factorial explicit:

- historical versus direct assembly at the same decimal and dyadic exact
  arithmetic holds the numerical primitives and representation fixed while
  changing the derivative/Taylor data flow;
- decimal versus dyadic execution of the same direct plan holds the data flow
  fixed while changing scale and rounding implementation.

The current generic dyadic/deferred lane is included as the integration gate.
The separately pinned outward-double direct plan supplies a lower-bound
comparison for the same complete formula.

## Outward-double direct plan

The old specialized C++ implementation first exposed a costly generic
univariate square-root dispatcher. Replacing it with the explicit identities

`sqrt(x)`, `1 / (2 sqrt(x))`, and `-1 / (4 x sqrt(x))`

inside the direct plan preserves all 4,173 certificate acceptances. On all
4,173 final bounds, the largest absolute difference from the old specialized
route is about `1.44e-15`. Twenty complete repetitions gave:

| Outward-double route | Preparation | Evaluation | Accepted |

| Old specialized object path | 0.000024108 s | 0.082313180 s | 4,173/4,173 |
| Generic composition | 0.000025143 s | 0.324809987 s | 52/4,173 |
| Direct source plan | 0.000004675 s | **0.060959726 s** | 4,173/4,173 |

The direct plan is 1.350 times faster than the old specialized object path
and 5.328 times faster than generic composition. Its profiled 0.062456-second
run attributes 0.021750 seconds to the six square-root leaves, 0.009021 to the
angle tangent, 0.024959 to the angle Hessian, and 0.002711 to final assembly.
After explicit square-root formulas, the angle Hessian and root leaves are the
two main numerical targets; final Taylor assembly is small.

## Proof decision

The direct exact specialization fails the material integration gate. A 5.3%
recurring or 2.1% cold-batch gain on one formula does not justify a new
case-specific proof layer. No standalone proof is started.

The source authenticator, direct primitive plan, and one-completion machinery
remain useful prototype components. They may be subsumed by a generally
proved instruction if a larger candidate wins, and a small already-near-
complete lemma may still close if it is directly reusable. The work packet
will not grow into separate per-expression calculus or Taylor proofs.

The outward-double result also improves the untrusted numerical lower bound
from 0.0823 to 0.0610 seconds. It does not erase the original approximately
341-fold observation: that value describes the original generic fixed-scale
route, whereas the latest ratios describe accumulated unproved native
specializations on one fixture. Nor does any native result reduce the
separate approximately 15-fold encoded-execution gap until the new algorithm
actually runs through `Kernel.compute`.

## Concrete larger-gap plan

The next work remains native and bounded:

1. Attribute the exact direct plan at the same root, angle-tangent,
   angle-Hessian, and final-assembly boundaries already measured in the
   outward-double plan. Existing profiles point directionally to exact
   dihedral and coordinate-root work; a matched direct profile will identify
   the first arithmetic primitive worth changing.
2. Keep the direct formula fixed while testing an outward endpoint backend
   with the same modern source plan, and test a division-reduced dyadic
   variant only where the exact profile identifies repeated non-shift
   normalization. Full 4,173-box acceptance, bound slack, recurring time,
   preparation, and memory remain mandatory.
3. Prefer generally reusable primitive instructions—coordinate square root,
   specialized dihedral enclosure, and compact centered-jet assembly—over a
   case-10173 theorem. Each instruction must have one universal containment
   theorem and source-reifier connection.
4. Require a material complete-batch win and a second expression/certificate
   family before investing in the complete proof-producing instruction set.
   The present 1.021-times cold gain is below that gate.
5. Only then port the winning exact instruction plan into `Kernel.compute` and
   remeasure numerical execution plus theorem handoff. That experiment, not
   native timing, tests the independent approximately 15-fold gap.

This keeps the orders-of-magnitude objective active while preventing a useful
local specialization from consuming the proof budget without evidence that
it scales.
