# v4.119: fast decimal refinement direction

Date: 2026-10-15 UTC

Status: DEVELOPMENT / NON-RELEASE evidence.

## Milestone correction

The genuine `matan` original theorem recorded in v4.117 used the generic
reflected evaluator.  It is an important correctness oracle, but its
hundreds-of-seconds execution cost does **not** satisfy the production
milestone that had been agreed: the specialized fast checker must imply the
original Flyspeck theorem without repeating the generic evaluation.

The specialized packed case-10173 checker remains the relevant performance
result: it accepted all **4,173/4,173** genuine cells in **10.24 seconds**.
The remaining production obligation is a refinement bridge from that fast
accepted verdict to the already authenticated HOL Light checker result and
then to the original theorem.

## Bounded decimal/dyadic discriminator

The existing HOL Light analytic/source soundness stack uses fixed scale
`10^12`, while the fastest CakeML checker prototype uses scale `2^40`.
Before duplicating the analytic proof stack for the dyadic representation, a
small verified experiment measured whether a decimal multiply-and-scale
primitive is actually slower in compiled CakeML.

The CakeML worktree now contains:

- `bounded_word64_mul_div_floor_decimal`, which computes the exact unsigned
  64-by-64 product, floors division by `10^12`, and returns two Word64 limbs;
- theorem `bounded_word64_mul_div_floor_decimal_correct`, proving the returned
  limbs reconstruct `(w2n left * w2n right) DIV 10^12`;
- verified CakeML translations of the primitive and repeated wrapper; and
- a closed 10,000,001-operation benchmark exported from that translated AST.

The arithmetic theory and translator theory both built successfully.  The
development executable was compiled with the existing direct `./cake` route;
no compiler bootstrap or per-program compilation theorem was claimed.
Disassembly confirms that the repeat loop calls the decimal primitive on each
iteration; the result was not replaced by one precomputed constant.

## Matched result

Seven balanced runs compared the new decimal primitive, the existing dyadic
multiply-and-shift primitive, and the existing control loop.  Each arithmetic
run performed 10,000,001 iterations.

| Lane | Mean wall | Control-subtracted wall |
|---|---:|---:|
| decimal `DIV 10^12` | **1.647143 s** | **1.518571 s** |
| dyadic shift 40 | **1.650000 s** | **1.521429 s** |
| control | **0.128571 s** | — |

The control-subtracted decimal/dyadic ratio is **0.9981×**.  At this primitive
boundary, decimal execution is therefore tied with the dyadic implementation;
the feared 2--3× penalty did not appear.  This does not yet measure a complete
decimal checker, and the binaries have different historical GC configurations,
so memory figures are not compared here.  The balanced recurring wall-time
result is sufficient to choose the next proof boundary.

## Decision

The shortest current production route is to preserve the fast specialized
algorithm while aligning its object-level arithmetic contract with the
already-proved decimal HOL Light checker.  The next implementation milestone
is:

1. extend the bounded decimal executor through the complete center/box,
   guard, certificate, and Taylor-verdict result used by the authenticated
   object checker;
2. prove representation/refinement from its accepted result to that object
   result;
3. use the existing soundness and `compute_with_thm` handoff to derive one
   original Flyspeck inequality theorem without generic reflected replay; and
4. measure a genuine multi-cell batch with shared preparation.

If complete-checker measurements reveal a material cost not visible at the
primitive boundary, the proved dyadic numerical contracts remain available;
the decision can be revisited from evidence rather than assumption.
