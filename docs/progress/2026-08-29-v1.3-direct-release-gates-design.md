# Direct S2/S3 release gates and honest resume design — 2026-08-29

## Conclusion

> Reviewed update, 2026-08-30: the original design correctly separated direct
> execution from PFT, but it did not fully separate direct S2 execution,
> direct S3 mathematical coverage, and release-level v1.3 S3 approval.  It also
> left cross-run projections and certificate consumption underspecified.  The
> corrected contracts below are prerequisites; no current schema-5 result may
> be promoted or supplied directly to a finalizer.

The current direct-source runner provides authenticated cumulative replay from
action zero.  It does **not** save or restore process/kernel state and therefore
does not satisfy v1.3 gates G6/G8 for a versioned checkpoint and materially
cheaper resume.  This is useful deterministic crash retry, but it must not be
renamed or promoted as checkpoint evidence.

A completely materialized verified HOL/CakeML state could satisfy the gate in
principle, but no such format exists here.  The smallest credible experiment is
therefore a provenance-bound DMTCP checkpoint of the compiled Candle process at
an exact cooperative source boundary.  DMTCP, its injected libraries, and host
kernel/vDSO semantics would be explicit trusted boundaries.  This experiment
must follow, not bypass, the direct evidence repairs below.

PFT remains a P1/oracle lane.  It is inadmissible in direct S2/S3 approval,
finalization, or checkpoint evidence.

## Evidence in the current implementation

`flyspeck_stratum_plan.py` declares eight cumulative prefixes with
`restart_mode=fresh-process-replay-from-action-0`,
`saved_process_or_kernel_state=false`, and
`checkpoint_replay_claim=false`.  Runtime receipts likewise record a null
process checkpoint and `fresh_process_replay_from_action_zero=true`; they keep
`s2_s3_evidence=false`.  The old HOL Light DMTCP helpers and the separate PFT
trace restart are not direct Candle release mechanisms.

At Candle `688d9d1738a7021501f95b6f0ed788e014fa726f`, schema 5 now implements
exact action outcomes, manifest-equal logical closure, loader-owned physical
source closure, fail-closed handling of the unused serialization-output route,
four ordered dependency-history observations, structural fingerprints, and an
unapproved semantic-coverage observation.  These controls are implemented but
unexecuted on a current linked runtime.  Schema 5 is intentionally
nonpromotable and remains insufficient for S3 because its 39 LP certificates
are authenticated as present but explicitly not consumption-traced.

## Prerequisite runtime evidence repairs

The original items 1--4 below describe the implemented schema-5 foundation.
They remain useful requirements and must pass in real runs, but are no longer
missing source implementation.  The new pre-checkpoint runtime requirement is
an exact certificate-consumption ledger (or an equally explicit reviewed
derivation) in a disjoint producer/validator schema.  Presence in the runtime
snapshot, final theorem fingerprints, or the schema-5
`lp_certificate_input_sha256` cannot be reinterpreted as consumption.

1. Each exact action marker must report its loader result.  A release run must
   accept only the reviewed `load` or ledger-backed skip result and must reject
   the current ambiguous `skip-loader-cache` path.  The outcome must be bound to
   the action identity and order.
2. The final run must emit and validate a manifest-equal logical source closure,
   including loader-owned/nested sources: every expected selected identity,
   no missing or extra identity, and an exact ordered digest.  The existing 297
   outer action attestations alone cannot prove this.
3. `serialization.hl` must not leave `Filename.temp_file` outside the evidence
   model.  Bind any generated digest file to an attempt-local exact output and
   its lifecycle, or fail closed on the unused save/load route.
4. Add a direct-specific fingerprint layer with reviewed
   `Serialization.full_digest_thm` dependency-history identities for the key
   theorems and an explicit source/LP/nonlinear coverage projection.  Label
   these honestly as dependency-history digests, not retained kernel traces.

Schema 2 and schema 5 evidence remain permanently nonpromotable.  Any stronger
clean-release or resume evidence has a disjoint version and fail-closed parser
tests for hidden skips, missing/extra nested sources, reorder/tamper,
generated-output mutation, certificate omission, intermediate-prefix
relabeling, and PFT injection.

## Independent semantic approval and finalization

Direct S2/S3 needs a separate non-PFT reference lane rather than overloading the
Great100 S1 approval schema.  Two nonce-distinct clean pristine OCaml/HOL Light
runs should collect the same direct boundary identities under the same
serializer while binding original sources, normalization policy, manifest,
generated inputs, tools, and ELF environment.  A reviewed direct identity
approval binds both raw candidates and the reviewer decision.

The equality projection is exact and intentionally narrow: serializer
identity; the four final-boundary theorem fingerprint records in order;
structural post-state; and the four ordered
`Serialization.full_digest_thm` dependency-history records.  Sources,
normalizations, generated inputs, tools, heads, and runtime closure bind each
raw candidate but are not folded into semantic equality.  Nonces, paths,
timestamps, and resources are excluded.

Coverage comparison uses a second canonical nonce-free projection.  It must
bind the exact 297 action outcomes, logical and physical source coverage,
generated inputs, nonlinear/LP/final-premise coverage, and certificate
consumption without hashing nonce-bearing observation envelopes.  Two honest
runs are not required to have byte-identical raw `semantic_coverage` objects,
because the current physical observation includes the attempt nonce.

A project-side direct finalizer should then follow S1's semantic/replay controls
while using disjoint schemas: immutable staging, captured committed validators,
independent plan/source reconstruction, two clean-run agreement, one resumed
run, external finalization authorization, and a closed inventory.  It must
consume only the exact full boundary `07-final_assembly-through-296` with 297
actions; a scheduling-consumer PASS for any earlier ordinary boundary is not a
finalizer input.

Claims are separate fields: `direct_s2_execution_approved`,
`direct_s3_coverage_approved`, and `v1_3_s3_release_approved`.  Direct S3
coverage additionally requires nonlinear, LP, and certificate-consumption
closure.  Release-level S3 may be true only after a separate machine-validated
release-evidence manifest closes every governing S3-required G1--G9 row and
mandatory mutation, relocation, resource, checkpoint, assumption, and
machine-code-boundary artifact.  Every layer requires `pft_used=false` and
rejects PFT artifact kinds.

The finalizer must re-run the authenticated direct validator and capture the
exact result tree while its plan/result directory descriptors and shared build
lock remain held.  It must use parent-directory identity binding,
no-replace publication, post-rename inode validation, parent fsync, and retain
failed staging.  The older S1 finalizer's path-only final check, plain rename,
and deletion of failed staging are not copied.

## Checkpoint pilot and qualification

After the evidence repairs, add one predeclared nonfinal cooperative boundary.
The process emits and flushes `READY` after its exact ledger/fingerprint marker
and blocks before the next action.  A controller launched under pinned DMTCP
captures it, kills the origin, atomically publishes a fresh read-only
content-addressed image set, restarts with a fresh nonce/token, and requires
`RESUMED` before the next exact action.

Qualification starts on a small compiled fixture.  Before the timing pilot,
freeze the boundary-selection rule, clean-run comparator, wall/CPU/RSS/disk
metrics, and a numerical acceptance threshold for "materially cheaper" resume.
A diagnostic full-run timing pilot then selects one boundary before release
attempts; there is no post-hoc boundary cherry-picking.  The release
qualification requires two clean full direct attempts and one kill/restart
attempt with byte-identical final semantic
and coverage projections, complete tool/library/image inventories, image
corruption and omission rejection, source/input/certificate mutation rejection,
whole-tree relocation, and measured wall/CPU/RSS/disk savings.  Aggregate
project use remains below the 120 GiB exceptional ceiling.

Suggested disjoint records are
`candle-flyspeck-process-checkpoint-v1` for the captured-but-unpromoted atomic
image set and `candle-flyspeck-resume-attempt-v1` for its nonce-distinct resumed
suffix and final result.  A cumulative source replay can never produce either
record.

## Principal risks

- DMTCP compatibility with the linked CakeML binary is not yet established.
- DMTCP injection conflicts with the current no-`LD_*` policy and needs an
  explicit checkpoint-mode trust declaration.
- Absolute paths in attempt configuration may defeat whole-tree relocation.
- A pristine OCaml full-source collector must model shell/filesystem and
  generated-input behavior that the existing S1 target collector does not.
- Closing nested source identities may initially expose legitimate preload or
  loader behavior; diagnose it before pinning, never silently whitelist it.
- A direct run can close execution/coverage while unrelated v1.3 compatibility
  or release rows remain open; claim separation must prevent that narrower
  success from becoming release-level S3.
