# Direct S2/S3 release gates and honest resume design — 2026-08-29

## Conclusion

The current direct-source runner provides authenticated cumulative replay from
action zero.  It does **not** save or restore process/kernel state and therefore
does not satisfy v1.3 gates G6/G8 for a versioned checkpoint and materially
cheaper resume.  This is useful deterministic crash retry, but it must not be
renamed or promoted as checkpoint evidence.

A completely materialized verified HOL/CakeML state could satisfy the gate in
principle, but no such format exists here.  The smallest credible experiment is
therefore a provenance-bound DMTCP checkpoint of the compiled Candle process at
an exact cooperative source boundary.  DMTCP, its injected libraries, and host
kernel/vDSO semantics would be explicit trusted boundaries.  This experiment
must follow, not bypass, the direct evidence repairs below.

PFT remains a P1/oracle lane.  It is inadmissible in direct S2/S3 approval,
finalization, or checkpoint evidence.

## Evidence in the current implementation

`flyspeck_stratum_plan.py` declares eight cumulative prefixes with
`restart_mode=fresh-process-replay-from-action-0`,
`saved_process_or_kernel_state=false`, and
`checkpoint_replay_claim=false`.  Runtime receipts likewise record a null
process checkpoint and `fresh_process_replay_from_action_zero=true`; they keep
`s2_s3_evidence=false`.  The old HOL Light DMTCP helpers and the separate PFT
trace restart are not direct Candle release mechanisms.

The existing boundary fingerprint foundation is useful: later boundaries
request LP, nonlinear, Flyspeck implication, Candle L2, and structural post-state
identities.  It remains deliberately uncompared and unpromotable.  It also does
not yet close every source-loading outcome, generated runtime input, dependency
history, or S2/S3 coverage claim.

## Prerequisite runtime evidence repairs

These are required before checkpoint engineering:

1. Each exact action marker must report its loader result.  A release run must
   accept only the reviewed `load` or ledger-backed skip result and must reject
   the current ambiguous `skip-loader-cache` path.  The outcome must be bound to
   the action identity and order.
2. The final run must emit and validate a manifest-equal logical source closure,
   including loader-owned/nested sources: every expected selected identity,
   no missing or extra identity, and an exact ordered digest.  The existing 297
   outer action attestations alone cannot prove this.
3. `serialization.hl` must not leave `Filename.temp_file` outside the evidence
   model.  Bind any generated digest file to an attempt-local exact output and
   its lifecycle, or fail closed on the unused save/load route.
4. Add a direct-specific fingerprint layer with reviewed
   `Serialization.full_digest_thm` dependency-history identities for the key
   theorems and an explicit source/LP/nonlinear coverage projection.  Label
   these honestly as dependency-history digests, not retained kernel traces.

The first implementation slice is limited to items 1–3 in a separate branch.
Schema-2 evidence remains permanently nonpromotable; any stronger evidence has
a disjoint version and fail-closed parser tests for hidden skips, missing/extra
nested sources, reorder/tamper, and generated-output mutation.

## Independent semantic approval and finalization

Direct S2/S3 needs a separate non-PFT reference lane rather than overloading the
Great100 S1 approval schema.  Two nonce-distinct clean pristine OCaml/HOL Light
runs should collect the same direct boundary identities under the same
serializer while binding original sources, normalization policy, manifest,
generated inputs, tools, and ELF environment.  A reviewed direct identity
approval binds both raw candidates and the reviewer decision.

A project-side direct finalizer should then follow S1's good controls while
using disjoint schemas: immutable staging, captured committed validators,
independent plan/source reconstruction, two clean-run agreement, one resumed
run, external finalization authorization, and a closed inventory.  S2 and S3
are separate booleans; S3 additionally requires LP, nonlinear, and certificate
coverage.  It must require `pft_used=false` and reject PFT artifact types.

## Checkpoint pilot and qualification

After the evidence repairs, add one predeclared nonfinal cooperative boundary.
The process emits and flushes `READY` after its exact ledger/fingerprint marker
and blocks before the next action.  A controller launched under pinned DMTCP
captures it, kills the origin, atomically publishes a fresh read-only
content-addressed image set, restarts with a fresh nonce/token, and requires
`RESUMED` before the next exact action.

Qualification starts on a small compiled fixture.  A diagnostic full-run timing
pilot selects one boundary before release attempts; there is no post-hoc
boundary cherry-picking.  The release qualification then requires two clean
full S3 attempts and one kill/restart attempt with byte-identical final semantic
and coverage projections, complete tool/library/image inventories, image
corruption and omission rejection, source/input/certificate mutation rejection,
whole-tree relocation, and measured wall/CPU/RSS/disk savings.  Aggregate
project use remains below the 120 GiB exceptional ceiling.

Suggested disjoint records are
`candle-flyspeck-process-checkpoint-v1` for the captured-but-unpromoted atomic
image set and `candle-flyspeck-resume-attempt-v1` for its nonce-distinct resumed
suffix and final result.  A cumulative source replay can never produce either
record.

## Principal risks

- DMTCP compatibility with the linked CakeML binary is not yet established.
- DMTCP injection conflicts with the current no-`LD_*` policy and needs an
  explicit checkpoint-mode trust declaration.
- Absolute paths in attempt configuration may defeat whole-tree relocation.
- A pristine OCaml full-source collector must model shell/filesystem and
  generated-input behavior that the existing S1 target collector does not.
- Closing nested source identities may initially expose legitimate preload or
  loader behavior; diagnose it before pinning, never silently whitelist it.
