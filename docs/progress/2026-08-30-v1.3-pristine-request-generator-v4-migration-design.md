# Pristine request-generator post-V3 migration design (2026-08-30)

## Status and prerequisite

This is a design-only reservation of a disjoint pristine raw V4 generation.
It is based on the independently accepted exact startup/full-run design
commit `c7d9a1c689b49b6e4f2815563887cbb948775a59`, whose
`docs/progress/2026-08-30-v1.3-pristine-startup-ledger-boundary-audit.md`
bytes have SHA-256
`1139ede64dd164294d35f2b5849889610dcf2070bf4f6ae4da65fe136f4185ec`.
Hostile review of that exact commit reported no P0, P1 or P2 finding.  Later
commit `23ccfa358fd6140337e50e715f3e931e8e2bd011` records that acceptance but
does not change the reviewed execution design.  The launcher, filter,
collector and receipts remain unimplemented and blocking.  This report does
not implement them or make a fallback route acceptable.

The migration answers the four integration blockers recorded at exact clean
request-generator commit `d3ed018b252921374db666cffbb06c957028e1b3`:

1. generator, fixed-loader and Python authority are absent from V3;
2. stock source MD5 and LP basename markers do not bind consumed bytes;
3. executing `request.ml` on OCaml stdin inserts toplevel results between
   reserved markers; and
4. the V3 parser mistakes ordinary successful declarations such as
   `exception Sanity` for process failure.

No V3 object may be relabelled.  V4 is not consumable until the protocol,
fixed loaders, parser, full-run collector, canonical validators and hostile
tests below all exist at reviewed exact commits.  No live pilot is authorized
by this report.

launcher drains this pipe and stdout/stderr to EOF, waits for the exact child,

return value, host file, inherited stdout, or caller-supplied payload cannot
