# Pristine request-generator post-V3 migration design (2026-08-30)

## Status and prerequisite

This is a design-only reservation of a disjoint pristine raw V4 generation.
It is based on the independently accepted exact startup/full-run design
commit `c7d9a1c689b49b6e4f2815563887cbb948775a59`, whose
`docs/progress/2026-08-30-v1.3-pristine-startup-ledger-boundary-audit.md`
bytes have SHA-256
`1139ede64dd164294d35f2b5849889610dcf2070bf4f6ae4da65fe136f4185ec`.
Hostile review of that exact commit reported no P0, P1 or P2 finding.  Later
commit `23ccfa358fd6140337e50e715f3e931e8e2bd011` records that acceptance but
does not change the reviewed execution design.  The launcher, filter,
collector and receipts remain unimplemented and blocking.  This report does
not implement them or make a fallback route acceptable.

The migration answers the four integration blockers recorded at exact clean
request-generator commit `d3ed018b252921374db666cffbb06c957028e1b3`:

1. generator, fixed-loader and Python authority are absent from V3;
2. stock source MD5 and LP basename markers do not bind consumed bytes;
3. executing `request.ml` on OCaml stdin inserts toplevel results between
   reserved markers; and
4. the V3 parser mistakes ordinary successful declarations such as
   `exception Sanity` for process failure.

No V3 object may be relabelled.  V4 is not consumable until the protocol,
fixed loaders, parser, full-run collector, canonical validators and hostile
tests below all exist at reviewed exact commits.  No live pilot is authorized
by this report.

Generation retains this exact order:

1. require `FLYSPECK_SERIALIZATION` absent and emit one nonce/ordinal/boundary
   session start;
2. emit the initial stock `loaded_files` snapshot as consecutive native events
   with phase `startup`; it must not synthesize `hol.ml` and must not contain

5. compare all 297 request targets positionally with
   `Build.build_sequence_full`, execute actions 0 through 177, install the LP
   wrapper, execute 178 through 183, set the retained certificate root, and
   execute 184 through 296;
6. emit exactly one ordered action-complete marker after every successful
   action, and exactly 39 unique successful-return-only LP markers during
   action 184;
7. load final target and serializer in that order, with exactly their two
   phase-`post-action` native events;
8. emit four theorem, one post-state, four dependency and one semantic
   terminal record with no intervening reserved or ordinary output generated

9. emit one session completion marker, flush, and allow no later byte.

The positional script route suppresses OCaml's interactive phrase-result
printing.  The generator should nevertheless render the semantic and terminal
tail as one explicit noninteractive control block or otherwise test that its
own code emits no ordinary byte inside that reserved tail.  Grouping phrases
without changing the stdin route would not be an acceptable repair.

## Reserved-marker-only output parser

The V4 parser first enforces immutable `bytes`, stdout cap and exact-empty
stderr.  It retains and hashes stdout byte-for-byte.  It splits for marker
recognition only at LF.  A line beginning an exact reserved namespace is ASCII
and tab-decoded; every other line remains opaque bytes and is never classified
by English words.

The reserved namespaces are exactly:

- `CANDLE_PRISTINE_DIRECT_` for the V4 grammar; and
- `CANDLE_PFT_` or `PFT_` at byte offset zero for forbidden PFT control
  records.

An unknown, legacy, malformed or wrong-nonce line beginning
`CANDLE_PRISTINE_DIRECT_` rejects.  Any line beginning either reserved PFT
prefix rejects.  Other appearances of the letters `pft`, `success`, `failed`,
`error`, `exception`, `pass` or `completed` in opaque ordinary output neither
accept nor reject and create no field.  In particular, `exception Sanity` and
`exception Unsolvable` remain ordinary retained bytes.  An unknown
`CANDLE_` control prefix also rejects rather than becoming ordinary output.

Only reserved V4 records drive the strict start/baseline/strictbuild/action/LP/
post-action/semantic/terminal state machine.  The session completion is the
last reserved record and its returned write interval is also the final stdout
bytes; partial records, missing LF, duplicate completion or any later byte
reject.  The non-TTY environment has exact color-disabled settings in the
full-run environment receipt.  Ordinary bytes are opaque, but reserved marker
bytes remain printable ASCII/tab/LF with canonical decimals and existing
field-size/count caps.

## Source MD5/parser joins

`candle-flyspeck-pristine-source-consumption-joins-v1` content-bound value with

`private_root_receipt`, `full_run_trace`, `record_count`,
`ordered_record_sha256`, `records`, `unsupported_count`, and the three false
promotion/PFT fields.

Each source record has exactly:

```text
index, native_event_index, phase, action_index, logical_source,

digest_open_event_indices, parser_open_event_indices,
digest_fd_generations, parser_fd_generations,
emitted_ledger_md5, supervisor_md5, supervisor_sha256,
all_opens_same_inventory_object, stock_success_event_observed
```

Indexes/counts are exact non-bool integers.  Digest and parser event/fd lists
are nonempty for a newly loaded source, equal-length to their corresponding
event roles, strictly increasing and bounded by the full-run event count.
For an already-loaded selected action, its prior successful source record is
referenced by the action binding and later digest-only probes remain in the
full event stream rather than inventing a second success record.

All recorded opens resolve through the private root to the same immutable
inventory object.  The supervisor independently reads that object and computes
both stock MD5 and SHA-256.  `supervisor_md5 = emitted_ledger_md5 = md5`, and
size/SHA-256/MD5 equal the authenticated inventory record.  Basename plus MD5
never selects a SHA-256 record by itself.  The exact authenticated stock
loader/strictbuild implementation establishes that a ledger append follows
successful parsing; the trace establishes that every content open available
to those operations names only the immutable joined object.  The rule covers
startup dependencies, strictbuild, all actions, final target and serializer.

The baseline closure derives its count/digest from phase-`startup` records,

joining the authenticated startup source with the stock-ledger closure; it may

## Full-run evidence closure and consumers

The V4 native/full-run closure adds exact content references named
`private_root_receipt`, `full_run_trace`, `task_tool_closure`,
`mutable_output_closure`, `request_script_binding`, `empty_stdin_binding`,
`source_consumption_joins`, `lp_deserializer_joins`, and `terminal_capture`.
Each equals a public canonical-byte-validated receipt produced under the
corresponding plan contract.  The closure also binds plan, request, raw
transcript, request-generation receipt and exact process result.  It cannot be
constructed by the pure stdout parser alone.

Large event streams are not one unbounded JSON value.  Each stream has a
canonical root manifest of at most 67,108,864 bytes and at most 4,096 ordered
chunks; each chunk is independently at most 67,108,864 bytes and uses closed
canonical length-prefixed records.  The manifest binds exact record/chunk
counts, total bytes, per-chunk byte/SHA-256 records, a domain-separated ordered
chunk digest and a domain-separated ordered record digest.  Total retained
stream bytes are at most 274,877,906,944.  Validators check caps before
allocation and stream chunks rather than materializing the maximum.  Exceeding
these constants requires a later disjoint schema; an implementation may not
silently raise them.

Every one of the nine V4 execution contracts and receipts binds the accepted
startup-design content record above.  In particular, the full-run trace
contract has one exact current-host kernel profile and requires the following
state, not merely a generic claim that syscalls were traced:

1. The fixed trusted bootstrap task blocks on the supervisor's empty gate,
   enters the exact `PTRACE_SEIZE`/`PTRACE_INTERRUPT` initial stop, and binds
   PID/start ticks, gate descriptors and initial
   `NoNewPrivs=1,Seccomp=0,Seccomp_filters=0`.  The idempotent no-new-privs
   call, exact captured BPF installation and post-state
   `NoNewPrivs=1,Seccomp=2,Seccomp_filters=1` are traced.  Resume mode changes
   from bootstrap `PTRACE_SYSCALL` to `PTRACE_CONT`; the exact probe SECCOMP
   event binds return data and syscall information, then every ordinary
   mediated entry is SECCOMP-event to `PTRACE_SYSCALL` exit to
   `PTRACE_CONT`.  Successful exec uses its separately closed event state.
2. Before the observer copies syscall information or any pointer-referenced
   path, argv or structure, it all-stops every `CLONE_FILES` sharer and
   `CLONE_VM` peer.  Those peers remain stopped through the matching same-task
   exit, fd duplication, logical-edge/object binding and atomic trace-state
   commit.  The selected pilot normally has no such peer except the one bound,
   already stopped vfork parent; an unexpected peer rejects.
3. Pre-baseline process creation rejects.  Later creation is limited to exact
   planned fork-equivalent calls, the authenticated dash
   `CLONE_CHILD_SETTID|CLONE_CHILD_CLEARTID|SIGCHLD` profile, and the exact
   pinned OCaml
   `CLONE_VM|CLONE_VFORK|CLONE_CLEAR_SIGHAND,exit_signal=SIGCHLD` profile.
   `CLONE_FS`, `CLONE_FILES` and every other sharing flag reject.  Each child
   joins one SEIZE auto-attach event stop to its parent event in either reap
   order before resume.  The vfork parent remains stopped through child exec,
   `VFORK_DONE`, parent clone exit and later wait.  Clone child-TID state is
   retired on exec; later `set_tid_address` is traced and its kernel final
   clear is non-evidentiary.
4. Each successful object open binds a unique inventory logical-object ID,
   normalized relative edge below held root/parent descriptors, symlink
   decisions, mount ID, device/inode, required stable generation/version,
   mode, size and SHA-256.  Content equality never substitutes for the exact
   authorized edge.  Request, source, LP, task/tool and output join validators
   must dereference the recorded trace event and require equality of this
   complete identity tuple; they may not validate from a path, basename,
   inventory index or digest alone.
5. Mutable-output admission is symmetric.  No reader is admitted while a
   writer fd or writable shared mapping exists, and no later writer, truncate,
   rename-over or other mutation is admitted while any reader fd or readable
   file-backed mapping, including `MAP_PRIVATE`, of that generation remains
   live.  Non-`FD_CLOEXEC` fds and their roles survive exec; old mappings end
   on successful exec.  A new generation is published only after the exact
   reader/writer/mapping quiescence and anchored-object hash barriers.

The trace-root identity is not optional context.  A standalone canonical
receipt validator proves only closed shape, local caps and digest integrity.
Authenticated validity of any request/source/LP/tool/output receipt requires
descriptor-rooted cross-validation against its enclosing native closure's
exact full-run trace root and event records.  Event-index receipts without
that join cannot be spliced into a complete rederivation, bundle or pair.
The request-script, empty-stdin, source-join and LP-join field sets above
therefore include `plan`, `request`, `private_root_receipt` and
`full_run_trace`.  The closed task/tool, mutable-output and terminal-capture
receipts include the same four references.  Their context-free validators
check only canonical shape/content-reference syntax; their evidentiary
validators require a descriptor-rooted resolver, reopen all four objects and
derive every event and identity join.

The full-run trace covers the leader and every authorized shell, GP, CSDP or
other descendant from pre-exec through wait, including task/start-ticks,
parentage, clone/file-table state, seccomp/syscall state, exec/argv/environment,
fd generations, opens, reads, mappings, pipes, waits and exits.  The tool
closure joins every exec and read-only tool/data object to private-root
inventory and every invocation/output to its declared action role.  The
mutable-output closure uses the reviewed symmetric generation state machine
above.  Terminal capture binds the final marker write,
stdout/stderr drain, no later byte, exact-empty stderr, all successful waits,
task/process-group exhaustion and final full-run event digest.

The pure parser returns a V4 raw transcript and parsed marker projections, but
an explicitly incomplete diagnostic source rederivation keeps
`execution_evidence` null and therefore exposes none of the nine full-run
references.  It has `authentication_status = not-authenticated`, no
coverage/candidate, and every approval/PFT/S2/S3 field false.  Only the
descriptor-rooted collector may join retained bytes with the nine receipts,
construct the V4 native closure and complete source rederivation, then derive
coverage.  Candidate publication remains private and pending until a separate
terminal capture-completion object postflights every held descriptor and
receipt.  Bundle validation reopens actual `/` and the held attempt root;
value-only bundle/pair validation remains disabled.

Every plan, request, transcript, semantic completion, native closure,
complete/incomplete rederivation, pending candidate, capture envelope,
terminal completion, bundle and pair validator has an exact key set and
requires canonical JSON bytes.  Unknown fields, missing evidence references,
bool/int coercions, over-cap records, digest/count/order drift, content-record
splicing and trailing data reject.  The pair validator requires different
ordinals/nonces and attempt roots but exact equality of full authority,
