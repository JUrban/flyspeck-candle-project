## Existing-compute limb discriminator

The native hardware-width result did not authorize adding a word primitive to
the trusted evaluator. The proof-producing `Kernel.compute` language currently
has unbounded numerals and pairs, so the bounded follow-up compared two exact
representations inside that existing contract:

- one 68-bit natural product followed by exact division by `2^23`;
- the same value split into 30-bit limbs, with the low product divided by
  `2^23` and the cross/high products shifted exactly.

Inputs were `2^34 - 13` and `2^34 - 43`. Every lane repeated the operation
32,768 times. Both representations returned exactly
`144115187606093824` per operation, and every `Kernel.compute` result was a
closed theorem with no assumptions. The benchmark is committed on the Candle
development branch as `7dd38558`.

Candle's in-process clock is deterministic, so a read-only external observer
timed flushed phase markers. The first balanced run measured:

| Lane | First sample | Second sample | Mean |
|---|---:|---:|---:|
| Single natural | 0.096434146 s | 0.096616061 s | 0.096525104 s |
| Two limbs | 0.108083226 s | 0.102121693 s | 0.105102460 s |

The limb representation was 1.089 times slower. A second balanced run had one
first-lane scheduling/cache outlier. Excluding that 0.204-second first sample,
the three warm single-natural samples averaged 0.125032158 seconds and the
four limb samples averaged 0.132089458 seconds: the limb representation was
again slower, by 1.056 times. Combining the five non-outlying natural samples
and six limb samples gives a directional 1.083-times limb slowdown; it is not
used as a high-precision performance claim.

The decisive point is that the limb path did not produce a recurring win even
before charging pair construction, signed interval structure, range checking,
or the reusable representation proof. It therefore fails the bounded gate.
There will be no limb arithmetic engine or standalone limb proof.

## What the two performance gaps now say

The two historical gaps remain distinct:

1. the original exact-output native equations were about 15 times faster than
   their encoded Candle execution;
2. the original generic native fixed-scale route was about 341 times slower
   than the specialized historical C++ route.

Later untrusted native work has reduced the second ratio on this fixture, but
has not yet transferred that gain into a proof-producing checker. The useful
controlled results are now:

- in the historical C++ library on the genuine 4,173 boxes, changing the
  specialized dihedral route to generic composition changed 0.082490265
  seconds and 4,173 acceptances into about 0.326891 seconds and only 52
  acceptances; this holds that library's scalar representation fixed and shows
  a large algorithm/enclosure effect;
- in the current native harness with the derivative graph fixed, changing
  unrounded `long double` to `double` improved recurring execution by 1.490
  times, while deleting padded normalization contributed only another 1.085
  times;
- changing the current generic graph to the source-derived historical-formula
  graph did not win, so formula substitution alone is not a faithful port of
  the historical specialized checker;
- reconstructing hardware width from small limbs inside the existing
  proof-producing evaluator is now measured and rejected.

Thus arithmetic layout matters, but the strongest remaining signal is the
historical checker's complete specialized derivative/enclosure algorithm and
its low-work data flow. The Candle/native encoded-execution gap remains real,
but another scalar microkernel is not the next step.

## Next bounded native factorial

The next experiment will bridge the two implementations rather than add
another isolated primitive:

1. instrument the already hash-pinned specialized C++ run on a bounded genuine
   box set to export its complete-box stages: center value/gradient, box
   derivative bounds, Hessian/table use, Taylor remainder, final upper bound,
   and primitive counts;
2. implement the same complete-box data flow in the current native harness
   with hardware `double`, keeping the boxes and specialized algorithm fixed;
3. require full certificate acceptance, compare bound tightness at every
   exported boundary, and charge source/box preparation, recurring execution,
   total batch time, and memory separately;
4. only after the native port agrees at those boundaries, rerun that same data
   flow with exact outward dyadic arithmetic. This changes arithmetic while
   holding the derivative/enclosure algorithm fixed.

This two-stage comparison is the missing factorial. The previous
`historical-dihedral` lane is not sufficient because it reproduced formulas
inside the current theorem-shaped Taylor machinery rather than the complete
specialized C++ enclosure route.

If the faithful `double` port does not approach the specialized C++ batch, the
remaining cause is lower-level library layout/control and will be profiled
there before proof work. If it does approach C++ but the exact-dyadic crossing
loses badly, arithmetic representation is the limiting formal-design problem.
If both win materially with 4,173/4,173 acceptance, the proof target becomes
one authenticated complete-box instruction with a reusable soundness theorem,
not per-expression calculus proofs.

The already measured dyadic-rounding and deferred-completion lemmas remain
potential components of that instruction, but no standalone specialization
proof will expand before this full-batch gate.
