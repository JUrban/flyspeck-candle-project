## Why v208 cannot be the current continuation checkpoint

The earlier v208 design reaches a genuinely clean post-action-170 proof state,
but its action file contains actions 171--184 after the checkpoint barrier.
Candle reads the complete `#use` file into a token buffer before evaluating
its first phrase. Those already-buffered phrases retain v208's older overlay
table, which predates the committed source-173, source-177, and
source-181--183 repairs at Candle commit `67a224e`.

Run
`/project/flyspeck-candle-runs/v219-candle-use-interrupt-clean-boundary-probe-001`
tested whether a pending interrupt could discard that buffered tail. It could
not: after the wait was released, all remaining loaded-file phrases executed
before `Compilation interrupted` returned control to standard input. The final
probe log has 6,640 bytes and SHA-256
`fecbb3558eec654df2b2ac8ae83f4806e050913c17cd062d7406a080f040774e`.

Therefore v208 remains useful, faithful evidence for action 170 itself, but it
must not be released as the continuation for the current source batch. No
failed or partially loaded v208 state will be reused.

## Resource and replay decision

Running v208 and v220 concurrently uses two Candle CPU cores and about 36 GB
resident memory. Together with the protected native PFT oracle, project RSS
remains below the owner's 120 GB allowance and CPU use remains well below ten
cores.

This is not a replay after each individual fix. The source-171--183 batch is
coherent, committed, and focused-green. The second traversal is required
because the earlier checkpoint's buffered continuation cannot represent those
committed bytes. Keeping v208 lets its 2,201 completed cases answer the still
valid action-170 question; starting v220 in parallel avoids adding another
full traversal serially before real action 184 can begin.
