## Research-note assessment

The source observations in
`docs/advice/Candle_NL_Performance_Research_2026-09-25.md` were useful, but
they do not identify one measured explanation for the remaining reflected
nonlinear gap. The current code and the v1.86--v1.88 measurements divide the
observations into three groups.

Already addressed:

- the general centered-Taylor soundness theorem, source reifier, certificate
  erasure, exact split-tree cover, one computed batch verdict, and compact
  root handoff have passed on the genuine action-296 parent;
- expression and whole-box preparation are shared across distinct boxes;
- production submits a batch behind one reflected verdict, so it does not pay
  one large theorem reconstruction per leaf; and
- proof-producing untrusted square-root hint arithmetic was replaced by exact
  untrusted `Num` arithmetic while the reflected checker remained decisive.
  That retained v1.86 change improved 64-box preparation by 2.66--2.69 times.

Measured and not worth pursuing as primary explanations:

- changing the 128-cell GCD fuel representation took 0.0069 versus 0.0055
  seconds for 512 hard calls;
- constant and variable completion each took about 6 ms per genuine
  six-dimensional result;
- an explicit shared endpoint-product helper was about eight times slower;
  and
- a proved Hessian-only product projection had no stable throughput benefit
  on repeated genuine 1/8/64-box measurements.

Still credible:

- the cost of normalization and large exact arithmetic *inside* the genuine
  one-shot program, as distinct from construction of the GCD fuel;
- the cost of the general reflected evaluator relative to ordinary execution
  of the same centered, outward-rounded algorithm; and
- a fixed-scale or other proved bounded-precision backend if the first two
  measurements justify that larger investment.

## Eight-box genuine-program discriminator

A new diagnostic starts from the sealed action-296 Taylor-support checkpoint,
reuses one authenticated source preparation, and constructs eight distinct
exact subboxes of the genuine accepted cell. For each box it executes the
existing 54-instruction centered program one instruction at a time. Only the
operands required by the current instruction cross each diagnostic
`Kernel.compute` boundary.

The untrusted ML side scans each concrete result for rational counts and
integer sizes. These scans authorize nothing. Each final stepwise result must
equal the existing one-shot computation exactly, the ordinary certified
finish must accept it, and the global axiom set must remain unchanged.

The successful run produced:

```text
432 / 432 instruction records
8 / 8 box passes
8 / 8 exact one-shot matches
8 / 8 accepted verdicts
0 unclosed phases
2,253,704 KiB peak sampled RSS
```

All eight outputs had the same bounded shape after every instruction:

```text
100 rationals
310 numeric leaves
100 / 100 denominators equal to 10^12
40-bit denominators
35--52-bit maximum final numerators
```

This rules out persistent denominator growth *between* top-level
instructions on this real program. It does not measure the transient values
or the number of normalizations inside an instruction.

The one-shot mean agrees with the prior approximately 2.44-second genuine

The stepwise total is deliberately not a throughput proposal. It includes 432
kernel/theorem boundaries and about 101 seconds outside the timed instruction
markers, chiefly the diagnostic result scans. The marker timings are useful
for localization but should not be subtracted mechanically from the one-shot
time.

## Where the program is large

The genuine source has 54 top-level analytic instructions. Its 22 polynomial
instructions contain 176 lower-level polynomial instructions per box. Two
large blocks at indices 32 and 33 contain 39 and 85 lower-level instructions,
respectively.

Across the eight boxes those two blocks accounted for 12.090 of the 24.571
seconds attributed to polynomial instruction markers, and 21.6% of all
instruction-marker time. They also produced the largest final numerators, 45
and 52 bits. Their cost is broadly proportional to their lower-level program
length; the measurements do not show a runaway caused by retained exact
fractions.

The other marker totals were spread across addition, multiplication, square
root, inverse, and arctangent. GC, output conversion, and the artificial
per-instruction theorem boundary make those fine rankings too noisy to justify
source changes.

## Decision and next discriminator

No production arithmetic or proof definition changes as a result of this
profile. The note has already yielded one material retained improvement in
untrusted point-certificate preparation, while its cheapest syntactic
optimization candidates have now been bounded or rejected.

The next useful numerical experiment is narrower than a checker redesign:

1. capture the exact operands for polynomial blocks 32/33 and representative
   inverse, square-root, and arctangent instructions from several distinct
   boxes;
2. measure normalization count, Euclidean iterations, transient integer size,
   and execution time without manufacturing per-step result theorems; and
3. compare the same centered algorithm under ordinary execution and
   `Kernel.compute`, with exact output equality where the algorithm is meant
   to be unchanged.

If normalization dominates, a small diagnostic fixed-scale implementation can
test the potential gain before undertaking its reusable correctness proof. If
ordinary execution is fast while the reflected version remains slow, evaluator
specialization becomes the better target. The existing universal analytic
theorem and genuine-leaf/root integration remain the stable proof boundary in
either case.
