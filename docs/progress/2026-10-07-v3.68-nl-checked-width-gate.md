## Question

The v3.67 case-16594 factorial measured a 23.3-times difference between exact
MPZ fixed endpoints and padded hardware doubles on one identical generic
Taylor graph.  Its naive `int128` preflight overflowed.  The next bounded
question was whether an exact, overflow-checking fixed width large enough for
the real graph could recover a substantial fraction of the arithmetic gain.

The new lane uses Boost's checked signed 256-bit integer.  Every overflowing
operation throws; it does not silently wrap.  Program, boxes, certificates,
scale, rounding directions, instruction order, and acceptance predicate are
otherwise unchanged.

## Interpretation

This is a more useful proof target than the raw double discriminator.  It
preserves the exact fixed-scale outputs and detects overflow, while removing
most of the MPZ cost on this complete certificate.  It does **not** yet prove
that 256 bits suffice for every supported expression, box, or subdivision.
The production contract must be total and fail closed: either a static range
proof establishes the width for a prepared batch, or each primitive returns
an explicit overflow result and the checker takes an exact fallback.

The result also changes how the evaluator and arithmetic opportunities combine:

- current reflected fixed-nonlinear case-16594 computation: 225.806 s;
- native exact MPZ graph: 18.801 s, a 12.01-times boundary;
- native checked-256 graph: 5.220 s, a 43.26-times boundary; and
- native padded-double graph: 0.794 s, a 284.48-times diagnostic boundary.

Those ratios are not directly additive and the native paths are not proof.
They show, however, that a flat verified evaluator alone and a bounded exact
arithmetic representation address distinct, large costs.

## Updated bounded plan

1. Audit Candle's verified evaluator and generated CakeML runtime for an
   existing word or bounded-integer representation that can be covered by
   `Kernel.compute`.  Do not design a new numeric subsystem before establishing
   what the current trusted path can execute efficiently.
2. If an executable bounded representation exists, prototype the exact
   256-bit operations with explicit overflow in the small checker.  First
   require byte-identical outputs on all 875 jobs and the existing case-10173
   regression; then measure the actual reflected batch and theorem handoff.
3. If `Kernel.compute` necessarily expands bounded words back into the same
   arbitrary natural arithmetic, keep the exact flat-batch evaluator lane as
   the proof-safe target and investigate verified compiled execution as a
   separate architecture.  Native output must not become an oracle.
4. Before any general range theorem, add the recorded case-16594 `int128`
   overflow as a regression and measure maximum intermediate widths on varied
   real families.  A successful 256-bit sample is evidence, not a universal
   bound.
5. Keep the exact-angle specialization bounded at `d70c17ea`.  Its proof work
   can continue only if it supplies reusable source-correspondence machinery;
   the width/evaluator results now have the larger measured payoff.
