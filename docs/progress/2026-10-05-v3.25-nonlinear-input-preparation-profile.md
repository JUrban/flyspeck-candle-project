## Discriminating the preparation cost

The authentic sample contains **1,083** third-batch jobs: all 59 function-0
jobs and 1,024 function-1 jobs. Exact `Num` preparation and a native-float
proposal produced byte-for-byte-equivalent interval terms on all jobs, with
no assumptions or axiom growth. A print-suppressed run then separated the
costs by external UTC marker timestamps:

| Phase | Jobs | Observed elapsed time |
| --- | ---: | ---: |
| Source-domain endpoint normalization | 1,083 | about 59 s |
| Exact point-program evaluation | 1,083 | about 3 s |
| Native-float point-program evaluation | 1,083 | less than 1 s |
| Stable-cell record construction | 1,083 | less than 1 s |
| Function-0 raw job encoding | 59 | about 1 s |
| Function-1 raw job encoding | 1,024 | about 40 s |

This changes the optimization priority. Replacing exact point evaluation by
float would save only approximately three seconds per 1,083 jobs and would
add another numerical representation. Endpoint normalization and raw term
encoding dominate this part of preparation instead.

## Cause: discarded proof production

`candle_disjunctive_fixed_outer_domain_bounds` called
`candle_reflected_nl_normalize_vector` for both six-dimensional endpoints.
For Flyspeck float terms that function builds twelve
`Arith_float.FLOAT_TO_NUM_CONV` theorems, constructs vector equality
theorems, and validates them. The caller retained only the normalized terms
and discarded both equality theorems.

That proof work is necessary at the final source-theorem handoff, but not
while constructing an untrusted numerical proposal. The bounded repair adds
an exact data-only decoder using Flyspeck's existing
`More_float.num_of_float_tm`, and uses it only in fixed-outer proposal
preparation. The proof-producing normalizer remains unchanged in
`candle_reflected_nl_source_pass_with`.

The soundness boundary is therefore:

1. untrusted ML decodes exact endpoint data and constructs a proposed
   certificate;
2. the reflected checker accepts or rejects that certificate;
3. final handoff re-normalizes the live source domain with kernel theorems;
4. it requires exact `aconv` equality with the proposed lower and upper
   endpoints before returning the source theorem.

A wrong data decoder can cause rejection or an endpoint mismatch, but cannot
authorize a theorem.

## Remaining measured preparation cost

Two sealed runs separated the 1,024-job raw encoder into its exact payloads.
The staged encoding was `aconv`-equal to the existing one-piece encoder and
introduced no assumptions or axiom growth. An externally timestamped repeat
measured:

| Encoding phase | Observed elapsed time |
| --- | ---: |
| Widened outer intervals | about 14 s |
| Center intervals | about 23 s |
| Original source boxes | about 9 s |
| Cell assembly plus final job-list spine | about 0.24 s |
| Existing complete encoder, repeated as baseline | about 45.7 s |

The final list shape is not the bottleneck. Nearly all time constructs the
three `Cexp_pair` interval payloads required by the reflected evaluator. A
linear estimate for 13,978 cells is now about 10.4 minutes, still subject to
large-batch garbage-collection and sharing effects.

There is a real but bounded reuse opportunity. Source-box payloads depend on
the logical box and variable basis; center payloads additionally depend on
the shared point program; widened outer payloads additionally depend on the
proposal. They can therefore be reused across repeated certificate variants
with those identities unchanged. Moreover, each existing scan theorem
already retains the full encoded job term as an authenticated call argument.

Reusing those terms in a later complete-forest call would require an exact
job-order mapping across accepted source cells and newly refined children.
That would save minutes, whereas complete reflected computation currently
takes hours. It is not justified to perturb the active fourth-batch lineage
before its failure set is known. No general cache or new provenance layer is
being introduced. Exact point-program evaluation and final list construction
are not current optimization priorities.
