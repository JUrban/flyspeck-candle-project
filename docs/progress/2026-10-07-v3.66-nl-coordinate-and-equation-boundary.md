## Coordinate-root factorials

The v3.65 stage profile concentrated most of the current compact-checker time
in the seven constant and six coordinate-square-root terms.  Three bounded
factorials have now tested the plausible local explanations.

First, the already reported sparse path omitted all known zero gradient and
Hessian entries while preserving the rational derivative arithmetic and
certificate predicates.  Its exact digest matched the generic path, but its
noisy two-run mean improved by only 1.068 times.

Second, the new fixed-derivative path keeps the same sparse graph and genuine
certificates but computes

```text
d  = 1 / (2 sqrt(x_i))
dd = d * (-1 / (2 x_i))
```

through the existing outward fixed-scale primitives.  The rational sparse
path took 4.281027709 and 4.290701163 seconds; the fixed-derivative path took
5.313196832 and 3.216360464 seconds.  Their means are 4.285864436 and
4.264778648 seconds, a negligible 1.005-times difference in favour of the
fixed path and much smaller than the order/caching variation.  This candidate
does not earn a soundness proof.

Third, an explicitly untrusted diagnostic bypassed the square-root domain
predicates while retaining the same fixed derivative arithmetic.  On the
same 128 genuine jobs its result digest was exactly equal to the checked
result because every supplied certificate satisfies its domain.  Checked
calls took 7.325640017 and 4.342471720 seconds; unchecked calls took
4.184894009 and 5.716385628 seconds.  The two-run means differ by only 1.178
times.  This is an upper bound on the benefit of eliminating the predicates,
not an authorization to do so.  Certificate validation remains mandatory.

Together these results reject dense zero propagation, rational derivative
normalization, and the domain predicate as individual explanations of the
large coordinate-stage cost.  No coordinate-root specialization proof or
full-family run will be started from these candidates.

## Corrected two-gap interpretation

The original approximately 340-times generic native fixed-scale versus
specialized C++ observation remains an important diagnosis of the starting
architecture.  It is not the remaining native gap after the controlled
low-work experiments:

- exact `int128`/dyadic versus padded outward `double`, with the direct graph
  fixed, costs 1.628 times on all 4,173 case-10173 boxes;
- generic versus direct data flow, with padded `double` fixed, costs 1.087
  times; and
- the optimized exact direct native path is now only about 1.35 times behind
  the specialized historical C++ path on this fixture.

Thus it would be misleading to seek another 340-times scalar-native gain on
case 10173.  The broad remaining measured gap is the approximately 14--34
times cost of executing matched exact derivative graphs through Candle and
handing their result back as a theorem.  The present local tests show that
this gap is distributed rather than concentrated in one coordinate helper.

## Concrete larger-gap programme

The specialization proof remains bounded.  The historical operation and
compact plan are retained as exact-output diagnostics, but no case-specific
production proof starts from their approximately two-times complete-prefix
gain.

The next work is organized around two independent gates.

### Gate A: second-family native 2-by-2 factorial

Use an already captured, structurally different genuine certificate family
(case 16594 is the leading low-setup candidate) and measure one complete
accepted batch in four lanes:

1. generic data flow with exact outward fixed endpoints;
2. lowered/direct data flow with the same exact endpoints;
3. the generic graph with outward hardware endpoints; and
4. the lowered/direct graph with the same hardware endpoints.

This repeats neither the old case-10173 microbenchmarks nor an informal
arithmetic loop.  Holding one axis fixed while changing the other gives the
requested derivative/Taylor versus representation/rounding factorial on an
independent real workload.  Report cold reusable preparation, recurring
batch time, bounds/containment, subdivision count, memory, and complete
certificate acceptance separately.  A loss of acceptance or materially
looser enclosure rejects a fast lane.

### Gate B: evaluator representation and execution

Use the current exact-output 128-box call as the regression oracle while
changing only the computation boundary:

1. make dependency slicing routine for experimental large bundles, while
   retaining the unsliced equality control;
2. profile the verified evaluator at the operation/allocation boundary on the
   compact angle and coordinate batches, rather than adding more source
   formulas;
3. prototype one flat, compact batch representation whose interpreter keeps
   fixed endpoints and interval/jet temporaries as ordinary computed data and
   returns only an acceptance bit or compact bounds;
4. compare that identical low-work graph in native execution and
   `Kernel.compute`, including input construction, computation, handoff, GC,
   and required repeats; and
5. if layout alone cannot materially narrow the matched gap, investigate the
   verified `Kernel.compute` implementation/compiler boundary itself rather
   than enlarging the trusted base or accepting an unproved native verdict.

Any fast native preparation remains untrusted.  The authoritative result must
still be a kernel theorem obtained from checked equations or from a new route
with an equally explicit verified correctness argument.  A native result or
digest comparison is an oracle, never the proof.

The advancement gates remain deliberately demanding: a 128-box candidate
must materially beat the current compact checker and preserve every accepted
box; the complete family must then win with preparation charged at its actual
reuse scope; a second family must confirm the design before the reusable
source-correspondence and complete-box soundness proof receives substantial
investment.  Ultimately the decision measure is complete-certificate time,
not isolated evaluator throughput.
