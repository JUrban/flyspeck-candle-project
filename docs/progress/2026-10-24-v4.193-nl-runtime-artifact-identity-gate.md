## Why this gate was run

The current fast-NL sources and proof-connected kernel cone had already built.
The verified CakeML bootstrap cone had also produced stages through the four
machine backends.  A later metadata-triggered recovery regenerated `decProg`
and `to_flatProg`.  The preserved `to_closProg` artifact required the former
`to_flatProg` parent theory identity

```text
a3b86b6cab7a558a15ba4e6cb214ed29c7712b7b
```

whereas the regenerated parent had identity

```text
e20d3dd2f72369955b42ea73251516157eb3fa95
```

This is a generated-theory ancestry mismatch.  It is not evidence against the
4,173-cell checker, the registered dispatcher refinement, or the original
theorem adapter.  It nevertheless prevents safely reusing the preserved
compiler suffix: changing the recorded parent identity by hand would discard
the very coherence the verified build is meant to establish.

## Bounded recovery experiment

The only cheap historical hypothesis was that the two affected stages had
originally been generated with the pre-fix `cv_repLib` behavior.  The exact
old source was reconstructed temporarily and its SHA-256 was checked against
the historical HOL commit.  Only `decProg` and `to_flatProg` were then rebuilt;
no later compiler stage was started.

Results:

| Measurement | Result |
|---|---:|
| Total elapsed | **57m17s** |
| `decProg` theory time | **17m20s** |
| `to_flatProg` theory time | **22m16s** |
| Peak RSS | **41,296,056 KiB** |
| Exit status | **0** |
| Reproduced `to_flatProg` identity | `e20d3dd2f72369955b42ea73251516157eb3fa95` |
| Required preserved-suffix identity | `a3b86b6cab7a558a15ba4e6cb214ed29c7712b7b` |

The hypothesis is therefore false.  Restoring the old automation code did
not reproduce the lost parent identity.  A scan of every available CakeML
worktree found no remaining artifact with the required identity.

The current `cv_repLib` source and binary artifacts were restored after the
experiment.  Their saved and rebuilt hashes match exactly, both HOL and
CakeML repositories are clean at their intended committed heads, and the
translation source hashes and timestamps used for the experiment were
restored.  No qualified Great100/S1 byte was touched.

## Efficiency decision

No more path-, timestamp-, or individual-library experiments should be used
to try to revive the unavailable identity.  They no longer have a supported
causal hypothesis.  The direct `./cake` route has already served its intended
purpose: it established the numerical implementation and performance cheaply.
This is now the frozen proof-connected bootstrap boundary for which direct
prototype compilation is not a substitute.

The next coherent route is one suffix rebuild from `to_closProg` through
`compiler64Prog` against the now-current `to_flatProg` identity, preserving
each completed theory as a restart point.  Historical measurements put that
suffix in the roughly **20--24 hour** range on one core, with some individual
stages approaching the configured 150 GiB heap ceiling.  That is a long
integration build, but it is a single deterministic milestone rather than an
edit/debug loop.  It should begin only as an explicitly recorded integration
run with:

1. clean source and artifact-identity preflight;
2. one CPU and a 150 GiB heap limit;
3. per-stage durable logs and restartable completed artifacts;
4. no source edits while it runs; and
5. a hard stop on the first semantic or theory-load failure.

If the coherent suffix and x64 assembly build, the next gates remain the
post-strictbuild checkpoint, the exact genuine default-clock fast dispatch,
and two clean productions of the original case-10173 theorem.  Until those
gates pass, the project must continue reporting **0/1** fast original
theorems.
