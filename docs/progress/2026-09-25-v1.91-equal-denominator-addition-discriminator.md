## Question

The genuine action-296 instruction profile showed that every top-level result
is rounded to denominator `10^12`, while the current rational addition first
cross-multiplies denominators and then normalizes. A narrow candidate therefore
tested whether an equal-denominator branch could avoid those products and
reduce the remaining reflected numerical cost.

For operands with the same denominator predecessor, the candidate constructs

```text
((left-positive + right-positive,
  left-negative + right-negative),
 denominator-predecessor)
```

and then calls the unchanged checked normalizer. Unequal denominators fall
back to the existing addition. This candidate changes no theorem interface,
rounding boundary, guard, or certificate data.

## Genuine data and exact validation

The fixture starts from the sealed action-296 Taylor-support checkpoint. It
prepares eight distinct accepted subboxes, runs the retained 54-instruction

the exact computed Taylor results. Every operand has denominator `10^12`.

The reflected timing input repeats those pairs to 6,400 additions. Production
and candidate calls use the same equation set and compact checksum. A separate
400-pair reflected check requires every complete normalized rational result to

## Smaller transient integers, unchanged Euclidean work

An untrusted exact-arithmetic profile of the same 400 pairs measured the raw
input to normalization:

| Metric | Production cross-product | Equal-denominator candidate |
|---|---:|---:|
| Maximum numerator size | 76 bits | 36 bits |
| Maximum denominator size | 80 bits | 40 bits |
| Total Euclidean iterations | 8,358 | 8,358 |
| Maximum iterations for one pair | 32 | 32 |

Thus the candidate genuinely halves the largest transient integer widths at
this boundary, but it does not shorten the Euclidean paths.

## Reflected timing is flat and order-sensitive

The first successful run measured:

| 6,400 additions | Wall time |
|---|---:|
| Production | 0.839 s |
| Candidate | 1.095 s |

A fresh run repeated the calls in production/candidate/candidate/production
order:

| Call | Wall time |
|---|---:|
| Production | 0.988 s |
| Candidate | 1.062 s |
| Candidate repeat | 0.850 s |
| Production repeat | 1.147 s |

Across the three observations per implementation, production averaged 0.991
seconds and the candidate 1.002 seconds. The candidate is about 1.1% slower by
that aggregate, while the within-implementation ranges are much larger. It
has no stable measured advantage.

The broad variation is consistent with allocation/GC and call-order effects.
It also reinforces the earlier endpoint-sharing and Hessian-only results:
smaller source expressions or integers do not reliably imply faster execution
when an additional evaluator conditional/function path is introduced.

## Decision

The equal-denominator branch is **not integrated** into production arithmetic.
The exact match makes it a semantically plausible refinement, but its measured
benefit is absent. A new central branch and its proof/replay burden are not
justified by noisy flat timing.

This narrows the research-note diagnosis further:

- constructing the pair-valued GCD fuel is not material;
- equal-denominator cross-products double transient bit widths but are not,
  alone, a measured bottleneck;
- Euclidean iteration count remains unchanged by this shortcut; and
- more isolated helper rewrites are unlikely to explain the 2.38-second
  genuine one-shot cost.

The next informative architectural comparison remains ordinary execution of
the same complete centered algorithm versus its one-shot reflected execution,
or instrumentation inside the large polynomial blocks without adding one
kernel/theorem boundary per instruction. If ordinary execution is also slow,
a fixed-scale backend should be tested at the algorithm level rather than as
another local rational helper. If ordinary execution is fast, evaluator
specialization is the more credible target.
