## Prototype under test

The v3.72 ledger established a concrete type boundary on two complete real
families.  This prototype therefore changes representation, not the
derivative/Taylor algorithm:

- persistent endpoints, interval products/additions, dot products, and
  gradient bounds use Boost checked signed 128-bit integers;
- radius-squared Hessian accumulation, Taylor error assembly, scale-squared
  center recomposition, and the final directed quotient use checked signed
  192-bit integers; and
- both outward-rounded results are checked while narrowing back to the
  endpoint representation.

The program graph, dyadic scale, operation association, directed rounding,
boxes, and certificate acceptance are otherwise identical to the checked
256-bit control.  Any overflow still fails closed.  The native prototype does
not yet return overflow as data or invoke an exact fallback.

## Interpretation against the larger gap

The representation boundary is real and reusable, but it is not the whole
orders-of-magnitude result.  On case16594 the mixed exact lane remains about
3.1 times slower than the earlier padded-hardware discriminator.  More
importantly, the existing reflected complete batch took about 225.8 seconds;
the now-equivalent native mixed computation takes 2.45 seconds.  That widens
the measured verified-execution target to roughly 92 times on this family.
The comparison is architectural rather than a claim that all 92 times can be
recovered: the reflected and native representations/executors remain very
different.

For case10173, the original approximately 340-times number remains a starting
generic architecture comparison.  Specialized native algorithm work removed
most of that mathematical-work gap.  The present mixed-width result isolates
an additional checked-representation improvement; it does not reverse the
conclusion that algorithm specialization and verified execution are separate
problems.

## Next reflected boundary

The native gate is strong enough to retain the mixed-width design, but not to
paste native integers into the trusted path.  The next proof-producing packet
has two parts:

1. specify total signed bounded operations and a three-way result—accepted
   value, arithmetic overflow, or rejected certificate—using the current
   natural-number logic;
2. prove that successful 128-bit endpoint/192-bit accumulator execution is
   extensionally equal to the existing exact checker, while overflow safely
   delegates to that checker.

That theorem preserves a proof-safe fallback independently of how execution
is accelerated.  The current `Kernel.compute` executor has only unbounded
naturals and pairs, so a fast word implementation remains a separate CakeML
compute/executor/correctness extension.  Its performance gate is now concrete:
the complete theorem-producing batch must improve materially after all
preparation, result decoding, fallback, and theorem handoff are charged.

In parallel, flattening the existing natural-number reflected batch remains
the cheapest way to attack the much larger evaluator boundary without first
changing the compute value language.
