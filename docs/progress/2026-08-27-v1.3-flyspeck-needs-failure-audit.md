# v1.3 `flyspeck_needs` failure-edge audit — 2026-08-27

## Scope and conclusion

This resolves the previously identified contract mismatch at the design level;
it does not change the shared loader or prove an implementation.  Source
semantics are anchored to direct Flyspeck
`1ce0353008eba83d3c76ae9a25c3c242e4802d53`.  The compared generated contract
is the clean Candle loader commit
`02c3493f6df6cb4b0845b14994bacef0c05a8163`, manifest SHA-256
`b9cc303fcb6af8bf46ddabe18edfabb7ce266a64c17a2b42104e17ff79509056`.
Reference observations used OCaml 4.14.1.

The pinned helper and generated contract agree on the accepted path and the
already-loaded path.  They do **not** have exact failure-path equivalence:

- a `false` result from `needb` makes pinned `flyspeck_needs` restore `host`,
  attempt `State_manager.neutralize_state`, remove the dependency edge, and
  raise `Failure`;
- an exception from `needb` escapes before `host` restoration and before
  neutralization, leaving `host` and `depend` changed;
- a `Failure` from neutralization is caught.  After a successful load, the
  source still records the file-table entry, prints success, and returns
  normally despite reporting a corrupted neutral state;
- a non-`Failure` neutralization exception escapes, after some state may already
  have been mutated.

The narrow release contract should not emulate those recovery quirks.  It
should explicitly be an **accepted-run exact, fail-closed failure refinement**:
evaluate a new authenticated target; abort the one-shot process immediately on
`false` or any evaluation exception; after `true`, call neutralization exactly
once and abort on any neutralization exception; record action success only
after both steps succeed.  An already-loaded target performs neither step.
This preserves the pinned successful observations while refusing to turn a
corrupted state into an accepted release.  The contract must stop calling this
exact failure compatibility and document the intentional strengthening.

For a new target, lines 193-214 perform these steps:

1. compute `id`; reject an existing circular `(host,id)` edge;
2. add `(host,id)` to `depend`, save `host`, and set `host := id`;
3. evaluate `let b = needb (flyspeckpath s)`;
4. only if that call returns, restore `host` and invoke neutralization inside a
   handler that catches `Failure` only;
5. on `b = true`, append the file-table count and print success;
6. on `b = false`, remove the dependency edge and raise
   `Failure ("Aborting Flyspeck Needs " ^ s)`.

There is no `finally` around step 3.  `load_on_path_b` adds `loaded_files` only
when `use_file_b` returns `true`, using short-circuit `&&`.  A `false` result can
nevertheless leave arbitrary effects from earlier successfully evaluated
phrases in the OCaml/HOL environment.

`neutralize_state` is also not transactional.  It clears the goal stack and
then resets overloads, interfaces, congruences, conversions, rewrites, binders,
prefixes, and infixes sequentially.  If a later operation raises, earlier
mutations remain.  Catching `Failure` around the whole call therefore does not
establish a neutral state.

## OCaml 4.14.1 reference observations

The reproducible oracle is
`tools/oracles/flyspeck_needs_failure_oracle.ml`, SHA-256
`9206488b0ce4c05c043babc629c55121ae01b96045be862eb3b9bd9febe932d5`.
Run it with:

```sh
ocaml -noinit -noprompt tools/oracles/flyspeck_needs_failure_oracle.ml
```

It uses compiler-libs' `Toploop.use_file`, temporary fixtures, and an injected
minimized transcription of the pinned outer control flow.  The asserted
observations are:

| Fixture | `Toploop.use_file` / `use_file_b` result | Observable effects before failure |
|---|---|---|
| two successful phrases | `true` | both effects |
| syntax error in the second phrase | `false` | none; the file is rejected before the first phrase executes |
| type error in the second phrase | `false` | the first phrase's effect remains |
| `Failure` or `Sys_error` raised by the second top-level phrase | `false` | the first phrase's effect remains; the exception is diagnosed by the toplevel, not re-raised to `use_file_b` |
| path absent at the `Sys.file_exists` test | `use_file_b = false` | none |
| existing directory supplied as the source path | raises `Sys_error "Is a directory"` | none |

Thus “source evaluation fails” is not a single OCaml outcome.  Parser/type/
runtime errors normally become the boolean `false`, whereas path and other I/O
conditions can raise before a boolean is returned.  The exact diagnostic text
and temporary filename are not proposed compatibility surfaces.

## Exact failure matrix

`loaded_files` is updated inside `load_on_path_b` before control returns
`true`; `ftable` is the separate constants-count table updated later by
`flyspeck_needs`.

| Trigger | `host` after exit | New `depend` edge | Neutralization | Load/file-table state | Overall result |
|---|---|---|---|---|---|
| target already loaded | unchanged | none | not called | unchanged | prints already-loaded and returns |
| `needb = false`, neutralization returns | restored | removed | called once | no new `loaded_files` or `ftable`; earlier phrase effects may remain | raises `Failure "Aborting..."` |
| `needb = false`, neutralization raises `Failure` | restored | removed | called; `Failure` caught and corruption printed | same as preceding row | raises the later `Failure "Aborting..."` |
| `needb = false`, neutralization raises another exception | restored | retained | called; exception not caught | no new table entries; earlier phrase effects may remain | neutralization exception escapes |
| `needb` raises (`Sys_error`, `Failure`, etc.) | remains the target id | retained | not called | no successful `loaded_files`/`ftable` update from this call | original exception escapes |
| `needb = true`, neutralization returns | restored | retained as dependency history | called once | `loaded_files` and `ftable` updated | success |
| `needb = true`, neutralization raises `Failure` | restored | retained | called; `Failure` caught and corruption printed | `loaded_files` and `ftable` still updated | **returns success** |
| `needb = true`, neutralization raises another exception | restored | retained | called; exception not caught | `loaded_files` remains updated; `ftable` is not updated | neutralization exception escapes |

The committed oracle asserts all outer-control rows except the already-loaded
short circuit and separately establishes the `use_file_b` result classes.

## Comparison with the current generated contract

The manifest currently says:

> if not already loaded, evaluate it and then call
> `State_manager.neutralize_state` exactly once after success; an already-loaded
> duplicate performs neither action

Its separate failure policy says failed loads abort.  This is directionally
correct for a release, but under-specified:

- it does not say that evaluator `false` and evaluator exceptions both abort
  without neutralization or later target execution;
- it does not say whether a neutralization exception is swallowed or aborts;
- “after success” differs from pinned source behavior when `needb = false`;
- it does not state that equivalence is limited to accepted runs.

The generated full-build program at the compared loader commit is SHA-256
`3b509d7187b49d557d080e5f07e9ca9b9e0c736c766cbb16178db8f3d83737bf`.
It remains inactive, so no present execution evidence resolves this ambiguity.

## Narrow contract update

Recommended replacement semantics for `required_loader_action`:

> At the directive position, authenticate and resolve only the manifest-selected
> target.  If it is already loaded, perform neither evaluation nor
> neutralization.  Otherwise evaluate it exactly once.  A `false` result or any
> evaluation exception aborts the entire one-shot release before
> neutralization, later targets, or a success marker.  After a `true` result,
> call `State_manager.neutralize_state` exactly once; any exception from that
> call also aborts before the action is recorded successful or a later target is
> evaluated.  Record success only after both steps return normally.

Add an assurance-limit field:

> This is exact for accepted and already-loaded observations and intentionally
> strengthens pinned failure behavior.  It does not preserve the pinned
> helper's post-failure state, diagnostics, attempt to neutralize after `false`,
> or swallowed `Failure` from neutralization.

This is the narrowest safe change: it clarifies the contract and tests without
changing accepted-route ordering, target selection, duplicate behavior, or
neutralization count.  Exact emulation of the pinned failed-run state should
not be a release requirement because partially evaluated files and partially
neutralized state cannot safely be reused.

## Hash-anchored regression plan

1. Regeneration must require the Flyspeck commit, both whole-file hashes, and
   all four relevant span hashes above.  The loader manifest/generator inputs at
   this audit point are `b9cc303f...` and
   `e12c4dfcfe361a671476400d42852b7c8898742867d51997cf350b9bf7234b4a`.
2. Keep the OCaml 4.14.1 oracle in CI and pin its SHA-256.  Assert boolean
   result, effect sequence, `host`, `depend`, `ftable`, and exception class;
   ignore random temporary names and formatter wording.
3. Unit-test the loader action with injected evaluator and neutralizer results:
   already loaded; `true`; `false`; evaluation `Failure`; evaluation
   `Sys_error`; neutralization `Failure`; and a non-`Failure` neutralization
   exception.  Assert exact call counts and that no later target runs on every
   failure.
4. In a three-target compiled integration fixture, make target A succeed,
   target B fail in each supported way, and target C write a sentinel.  Every B
   failure must yield nonzero process status, no success marker, and no C
   sentinel.  Include a B fixture that performs one effect before returning
   `false` to prove the contaminated process is terminated rather than reused.
5. On neutralization failure, assert that the action is not recorded successful
   even though source evaluation may already have populated loader state.  The
   release process must exit; rollback is not claimed.
6. Retain successful and already-loaded duplicate tests: successful evaluation
   and neutralization each occur once, while a duplicate invokes neither.
7. Freeze the assurance-limit wording in the manifest test so later work cannot
   silently upgrade accepted-run refinement into full failure-path equivalence.

## Validation and limits

The reference oracle passes under local OCaml 4.14.1.  `git diff --check` is
part of the project commit validation.  The oracle is a minimized reference
test, not a HOL execution proof; injected neutralization failures establish the
OCaml handler behavior, not the reachability of a particular real
`State_manager` failure.  No shared Candle, Flyspeck, CakeML, or HOL file was
modified.
