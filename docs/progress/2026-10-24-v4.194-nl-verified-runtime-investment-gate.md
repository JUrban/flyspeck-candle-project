## Decision

The current frozen verified-runtime suffix build is **GO for one bounded
attempt**.  This is not a claim that the first fast theorem is certain to
succeed.  It is a decision that the remaining integration hypothesis is now
specific enough, and the prerequisite evidence strong enough, to justify one
roughly 20--24-hour one-core bootstrap investment.

This authorization does **not** extend to a repeated day-long edit/test loop.
If the resulting runtime exposes a theorem or handoff defect, the defect must
first be reproduced and repaired in the minute-scale proof builds, direct
`./cake` executable, or a disposable restored Candle checkpoint.  Another
full bootstrap requires a separately recorded, cheaply validated runtime
source change.

## Why a new verified bootstrap is required

The first x64 assembly attempt stopped before producing `cake.S` because
`repl_decs_allowed` referred to an obsolete `candle_prover_inv` identity.  A
subsequent compiler-cone attempt reached `reg_alloc` after 8h12m but exhausted
its 100 GiB allowance.  A 150 GiB cone run then built through all four target
backends in 9h44m, but `compiler64Prog` correctly rejected a second stale
edge: `repl_check_and_tweak` still named obsolete `repl_decs_allowed` identity
`55720aec...`.  Thus that run established that the larger heap could traverse
the expensive suffix, but it did not produce a composable compiler theorem.

The current parent pair has now been regenerated coherently.  The present
`repl_decs_allowed` names current `candle_prover_inv` identity `bb2006f...`,
and present `repl_check_and_tweak` names current `repl_decs_allowed` identity
`9864b626...`.  Rebuilding the descendants from the first changed translation
node is required because the older descendant theories authenticate the old
parent identities; retaining them by hand would break the verified theory
graph.

Those are compiler artifact/resource failures, not failures of the NL
checker or theorem.  They nevertheless make hand-reusing the suffix
unsound.  The standard verified chain must therefore be rebuilt once from
the first unavailable descendant.  Direct `./cake` compilation was useful
for numerical development and timing, but it cannot substitute for the
proof-connected compiler/runtime artifact required by this gate.

This recovery cost was partly avoidable.  Per-stage immutable receipts and
artifacts are now mandatory so a later interruption resumes at the failed
stage instead of replaying completed work.

### Why the 20--24-hour projection is not a controller artifact

The projection is derived from the measured cost of the same verified theory
cone, not from multiplying a short job by an arbitrary safety factor.  The
three historical portions took 8h12m through the frontend before the 100 GiB
failure, 6h25m for `reg_allocProg` through `printingProg` before the next
resource boundary, and 9h44m for `to_word64Prog` through the four target
backends before the stale final parent link was rejected.  Those portions sum
to about 24h21m.

Invoking the theories one at a time does not introduce another copy of those
proof costs.  The earlier single-cone Holmake invocation also linked and ran a
fresh HOL theory-builder process for every theory, including the same
authenticated ancestor loading.  The first six current stage times are
comparable to, and in several cases below, their earlier theory-build times.
The added controller work is dependency scanning, hashing, and writing a
small receipt after each already-required builder, not another proof replay.
Stopping the coherent run merely to replace the controller therefore has no
measured speed advantage.  It would discard the simpler hard-stop boundary
and make stage-level resumption less explicit.

## Remaining untested joins

The investment is justified, but success is not known.  Four joins remain:

1. the current HOL representation-rule correction must propagate through the
   complete compiler suffix and x64 bootstrap;
2. the linked development runtime must start and reach the saved
   post-strictbuild checkpoint;
3. the exact genuine `Kernel.compute` call must take the installed fast hit,
   rather than reject, fall back, or expose a translation/precondition defect;
4. the previously exercised topology/original-theorem handoff must compose
   with that exact new numerical theorem in the current runtime.

Only join 1 consumes the present 20--24-hour projection.  Joins 2--4 are
performed from durable checkpoints; a failure there must not trigger another
bootstrap without a separately proven runtime-code cause.

## Bounded execution plan and stop rules

1. Keep CakeML, Candle, and HOL sources frozen for the full suffix build.
2. Build one theory at a time with a 150 GiB heap ceiling and one CPU.
3. After every successful theory, store its theory identity, data hash,
   elapsed time, peak RSS, and completion receipt.
4. Stop on the first failed theory and preserve the exact log; do not extend
   the architecture or start an alternate long build in the same response.
5. After `compiler64Prog`, build x64 `cake.S` and link a distinctly named,
   non-promotable development runtime pinned to the exact three repository
   heads.
6. Save the stable post-strictbuild, post-action-49, and post-fast-support
   checkpoints before invoking the changing one-call harness.
7. Run the exact one-call original-theorem test twice from fresh copies of the
   support checkpoint.  Require the exact call identity, theorem digest, zero
   assumptions, zero axiom growth, and identical results.  Require exactly
   one registered-numerical timing per run and a conservative maximum of 120
   seconds; this is far above the unchanged 7.35-second fast batch but below
   even one roughly 200-second generic cell replay, so a correct generic
   fallback cannot be mislabeled as the fast theorem.
8. If either theorem run fails, preserve it and diagnose from the nearest
   checkpoint.  Do not rebuild the compiler during theorem-level debugging.
