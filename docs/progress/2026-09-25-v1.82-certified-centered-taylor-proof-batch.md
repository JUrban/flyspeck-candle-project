## The reusable centered-checker soundness path is complete

The centered, fixed-scale, outward-rounded Taylor-model interpreter now has a
complete reusable proof chain for its supported analytic expression language:

1. the structural invariant is preserved by the compiler and every polynomial
   and analytic instruction;
2. each cached value, gradient, and Hessian enclosure is linked to the source
   expression over the authenticated box;
3. the executable certified boundary accepts only when all domain guards, box
   validity, and the final negative upper bound hold;
4. a general theorem turns acceptance into negativity of the denoted source
   expression throughout the box; and
5. the proof-producing adapter authenticates the center and box programs,
   executes the checker with `Kernel.compute`, instantiates the general
   theorem, and rewrites back to the original Flyspeck formula.

The checker consumes the cached outward-rounded whole-box value interval. It
does not reconstruct the superseded loose forward-jet bound and does not build
43 separately differentiated programs.

## Hard-coded analytic certificates did not generalize

The first four consecutive pass leaves from the authentic action-296 precision
tree were selected for a small batch. An initial bounded run reused the first
leaf's square-root intervals everywhere. Leaf 0 passed, but leaf 1 continued to
reject even after its computed upper bound had become negative. The failing
condition was a domain/certificate guard, not Taylor tightness.

That failure is preserved at:

```text
/project/flyspeck-candle-runs/
  cv-action296-taylor-batch-certified-v4-run-001
```

It exposed a data/code boundary error: `[38,80]` was a valid nested-square-root
proposal for the first genuine leaf, not a reusable expression-wide constant.
Further blind subdivision would not repair such a guard.

A small untrusted preprocessor now evaluates every square-root argument over
an original source box using exact rational interval arithmetic, then proposes
convenient rational square-root endpoints. Floating point only proposes the
endpoints. The reflected program checks their exact correspondence before any
theorem can be produced. One prepared box program is reused across every child
of that original leaf.

This makes explicit a useful longer-term boundary: box-specific analytic
enclosures are certificate data. They should eventually be checked as data by
the monolithic certificate checker rather than baked into separately compiled
programs.

## Measured cost boundary and compact-verdict direction

The external stage timestamps separate the current reflected work:

- per original leaf, exact interval certificate preparation and source-program
  authentication cost about 4.3--4.7 seconds;
- across 12 attempted cells, work before the `boxes-encoded` marker totals
  about 89 seconds, roughly 7.4 seconds per cell. This includes normalization,
  point-specific square-root preparation, point-program reification and source
  proof, and box serialization;
- the 12 actual centered `Kernel.compute` program executions total about
  27 seconds, roughly 2.1--2.5 seconds each;
- certified finishing is negligible; and
- after an accepted numerical result, evaluation linkage, acceptance
  extraction, soundness instantiation, source rewriting, and child theorem
  assembly cost roughly 0.4--0.8 seconds per accepted child.

The dominant recurring cost is therefore not rational evaluator execution or
final theorem handoff. It is rebuilding a point-specific authenticated program
for every attempted child. Small evaluator optimizations are not the priority.

Today, the following still happens through per-leaf or per-child theorem
construction:

1. one box-specific analytic program and source theorem per original leaf;
2. one center-specific analytic program and source theorem per attempted cell;
3. one computed evaluation equality per attempted cell;
4. one source negativity theorem per accepted child; and
5. explicit split/glue theorem construction back to the original leaf.

The natural compact-verdict destination is now concrete. A generally proved
certificate-tree checker should consume ordinary data containing:

- one authenticated source expression/program;
- original boxes;
- box-specific square-root enclosures;
- center data;
- subdivision axes and child boxes; and
- the final Taylor-model results.

It would validate the whole tree in one or a few `Kernel.compute` calls and use
one general tree-soundness theorem to return the original root theorem. The
source correspondence would be paid once. Intermediate centers, intervals,
and child verdicts would remain data rather than causing separate compiler and
source theorems. The current universal expression theorem already supplies the
analytic core; the missing reusable layer is certificate-tree soundness and a
data-level checker, not another calculus proof.

The next bounded step is to prototype that tree boundary on these same four
leaves and compare complete theorem time. Only after that should the batch be
expanded to more leaves or expressions.
