## Projection interpretation

The full archive census contains 23,807,813 numerical terminals. This sample
uses 314.45 / 534 = 0.5889 compute seconds per repaired cell and 431.75 / 534
= 0.8085 post-restore seconds per cell. A deliberately naive linear scaling
would be approximately:

- **3,894 CPU-hours** for complete evaluation alone; or
- **5,347 CPU-hours** for the measured post-restore route.

These are **not all-NL forecasts**: they use one supported sample, equate
archive terminals with repaired reflected cells, omit per-record fixed costs,
and do not model unsupported analytic functions or sample-stratum variation.
They are included only as a scale discriminator. They show that the stock
route is not the sought orders-of-magnitude acceleration and support keeping
the fast compiled theorem route as the production objective.

The archive records 850.878 historical seconds for this same source/index.
The present 431.75 post-restore CPU seconds are about 1.97x smaller, but the
machines, load, timing definitions, and implementations differ; this is an
orientation point, not a controlled cross-implementation speedup claim.

## Summarizer correction

The first committed summarizer invocation rejected the valid phase table
because it expected one `variable-complete-validation` marker pair. The real
route has two: one before complete evaluation and one before root handoff.
The summarizer now requires exactly two ordered pairs and reports
`validation` and `root_validation` separately. Its fixture test models the
actual marker sequence. No runtime or measurement byte was changed, and no
timing rerun was required.
