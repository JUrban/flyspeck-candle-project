## Assessment of the research note

The independent note
`docs/advice/Candle_NL_Performance_Research_2026-09-25.md` is a useful source
review. Its most important contribution is not a single diagnosed bottleneck,
but a good separation between numerical algorithm cost, generic evaluator
cost, reusable preparation, and theorem handoff. Measurements through v1.91
and the new discriminator below now classify most of its proposals.

### Already covered or materially improved

- The universal centered-Taylor soundness theorem, source reifier,
  certificate-erasure link, exact split-tree cover, one computed batch
  verdict, and compact root handoff are complete and have proved the genuine
  action-296 parent. There is no remaining per-expression calculus proof.
- Production returns one batch acceptance bit. It does not return the old
  full diagnostic trace or reconstruct one large numerical theorem per leaf.
- Authenticated expression and whole-box preparation are shared across
  distinct boxes. Production evaluates the boxes behind one reflected batch
  boundary, so repeated `Kernel.compute` setup is already amortized.
- Discarded proof-producing `REAL_RAT_REDUCE_CONV` work in square-root hint
  preparation was replaced by exact untrusted `Num` arithmetic, with the
  reflected guards still decisive. The retained v1.86 change improved
  64-box preparation by 2.66--2.69 times and the complete measured path by
  1.72--1.74 times.
- Stable analytic libraries and proof support are checkpointed. The long
  library load is not in the ordinary edit/experiment loop.

### Measured secondary or rejected explanations

- Numeric versus 128-pair GCD fuel took 0.0055 versus 0.0069 seconds for 512
  hard calls. The fuel representation cannot explain the batch time.
- Complete constant and variable results cost about 6 ms each on a genuine
  six-dimensional box. Their dense completion is real but not the main gap.
- Explicit endpoint-product sharing was about eight times slower than the
  current definition.
- A proved Hessian-only multiplication projection had no stable throughput
  benefit on repeated genuine 1/8/64-box batches and was removed.
- An equal-denominator addition branch halved transient integer widths but
  left Euclidean iteration counts unchanged and had no stable timing gain.
- The genuine instruction profile found bounded `10^12` denominators and
  modest 35--52-bit final numerators after every top-level instruction. There
  is no persistent denominator explosion between instructions on this case.

These negative results matter: source-level constructor counts and discarded
projections are not reliable timing predictions for Candle's evaluator.
Future arithmetic changes need whole-program measurements on distinct boxes.

## New exact-output discriminator

`Kernel.compute` exposes only a monolithic interface. Its internal validated
equation-table construction and executor are not callable separately from
Candle source. A small untrusted diagnostic executor was therefore added for
the same public compute-equation language. It compiles equation references to
array indices and supports the exact integer/pair primitives used by the
checker.

This executor is **not** a proof mechanism. It constructs no theorem and may
never authorize a result. A focused extended-rational test first required its
complete concrete result to equal `Kernel.compute`. The genuine experiment
then required all eight complete action-296 Taylor results to equal the
corresponding kernel result exactly; only the kernel theorems were used to
check acceptance.

Two fresh restores used eight distinct exact subdivisions of the genuine
accepted action-296 cell. Shared source and whole-box preparation were charged
once.

| Phase | First run | Repeat |
|---|---:|---:|
| Shared whole-box source preparation | 4.843 s | 4.568 s |
| Eight center/certificate variants | 16.126 s | 16.391 s |
| Diagnostic equation-table compilation | 0.0109 s | 0.0109 s |
| Eight input compilations | 0.319 s | 0.320 s |
| Eight ordinary diagnostic executions | 51.745 s | 52.579 s |

The instrumented ordinary executor was 2.59--2.63 times slower than Candle's
fast verified executor: about 6.47--6.57 versus 2.50 seconds per box. This does
not bound a specialized native implementation because the diagnostic remains
a generic AST interpreter and maintains counters on every operation. It does
show that merely moving the same equation interpreter outside `Kernel.compute`
is not a speedup. Candle's current fast executor already handles this generic
workload substantially better than that straightforward ordinary baseline.

algorithm a stronger target than equation-table setup.

## Revised priorities

1. **Keep the existing analytic proof boundary.** The general theorem and
   genuine-root integration are already the durable part of the design.

2. **Do not build a persistent compute context merely to remove setup.** The
   v1.90 constant controls measured about 40 ms per separate call, while
   production already uses one internal batch. The new equation and input
   compilation measurements are also small relative to numerical execution.

3. **Test fixed-scale arithmetic at an algorithm boundary, not through more
   local rational helpers.** The millions of divisions/moduli and much larger
   pair traffic make a direct scaled-integer backend credible. The next
   bounded prototype should cover at least the two large genuine polynomial
   blocks, preferably one complete box, retain directed rounding and guard
   behavior, and compare acceptance/bound tightness as well as time. Exact
   structural equality is not expected if the representation changes, so its
   output remains diagnostic until a reusable correctness theorem exists.

4. **Retain a specialized/native baseline as a later discriminator.** The
   present ordinary executor is generic and instrumented, so it does not rule
   out verified specialization or compilation. That larger work is justified
   only after the numerical backend avoids demonstrated rational/pair work;
   otherwise it risks specializing an unnecessarily expensive algorithm.

5. **Continue amortizing preparation.** Even after the retained improvement,
   center/certificate preparation is about two seconds per box here. The v1.86
   subprofile attributed most of this to seven exact square-root proposals and
   then proof-producing per-box program compilation. Precompiling the seven
   argument evaluators once per expression is the next small preparation
   experiment. Longer term, supplying checked certificate data separately
   from one shared compiled source could remove repeated variant compilation
   under a general erasure/patching theorem.

6. **Do not revisit isolated output/projection helpers without new evidence.**
   The compact verdict is already present, ordinary result conversion was
   below one second for eight complete results, and the endpoint/Hessian
   candidates were negative. Deeper representation changes are more credible
   than more source-local shims.

The note therefore helps explain the remaining gap, but the explanation is
now narrower: a large recurring numerical data workload plus still-visible
per-box certificate preparation, rather than long proof setup, repeated
kernel initialization, or theorem reconstruction. The next positive target is
a whole-algorithm fixed-scale discriminator; the next preparation target is
reusing square-root argument evaluators across boxes.
