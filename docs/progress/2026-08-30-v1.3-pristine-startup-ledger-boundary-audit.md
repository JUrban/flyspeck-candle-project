# Pristine startup versus loader-ledger boundary audit (2026-08-30)

## Finding

The accepted pristine raw protocol currently requires `candle:hol.ml` to be a
stock HOL Light `loaded_files` event before the original `strictbuild.hl`
event.  That requirement is not implementable by the planned pristine process
route.

In the pinned HOL Light source, `hol_loader.ml` initializes
`loaded_files = ref []`.  Only `load_on_path` appends a file identity after a
successful `use_file`; `loads` and `loadt` are wrappers around that function.
The top-level `hol.ml` is instead executed by OCaml's `-init` option before the
request source runs.  It loads its dependencies through `loads`, so those
dependencies can appear in `loaded_files`, but `hol.ml` never loads itself
through `load_on_path` and never appends its own identity.

This conflicts with the following current protocol facts:

- entrypoint step 0 starts pristine HOL Light from `candle:hol.ml`;
- step 1 installs the request-local native-ledger observer only after startup;
- `LOADER_LEDGER_POLICY` claims a stock `loaded_files` success ledger; and
- `validate_native_execution_closure` requires both `candle:hol.ml` and
  original `strictbuild.hl` in the bootstrap event slice, in that order.

The inspected inputs are content-fixed as follows:

- pinned `hol_loader.ml` SHA-256:
  `01d0f6b5a8ba557b58a352a464c25a408b80585a778d7cc61b11ea688290db29`;
- pinned `hol.ml` SHA-256:
  `9eabbd17397d942d116f1087e4b11d82746acc19ca77c11fed04046fdbec3e32`;
- reviewed pristine protocol SHA-256:
  `3c8fd6b5cfc2240a57ff45e3d1aa1592e3bb73f713101c975fa1dc4cd6f1fc84`;
- accepted semantic/capture design SHA-256:
  `e029cbf4b07e65865097a837fa7ec34dd297506548a3142583d4420b7be7a0e0`.

A generator could print a plan-bound `hol.ml` marker, but that would be a
synthetic startup claim, not a stock loader-ledger observation.  Relabelling it
as a native load would make the retained evidence internally well-shaped but
semantically false.  The step-4 request generator is therefore prohibited from
synthesizing this event, and no collector pilot is authorized under the
current closure contract.

## Evidence boundary affected

The startup source can still be authenticated, but by a different mechanism.
A held descriptor plus a recorded `-init /named/path/hol.ml` argument is not
sufficient: another same-UID process can replace the name for OCaml's open and
restore it before every later named-edge and descriptor check.  The collector
must instead bind the kernel execution route and make the consumed startup
bytes immutable independently of a mutable pathname.

The pinned `ocaml-hol` is itself an OCaml bytecode file with an
`#!/usr/bin/ocamlrun` interpreter line, not the kernel-executed ELF image.  A
complete receipt therefore has to distinguish and bind the `ocaml-hol`
bytecode, the actual `/usr/bin/ocamlrun` executable and its mapped dependency
closure, and the `hol.ml` startup source.  The accepted capture design's
child-binding field list currently has detailed PID, wait, descriptor,
descendant and namespace facts but no closed executable/argv/startup-source
observation.  Relying only on the authenticated collector's source code would
leave these execution facts implicit in the receipt.

The loader ledger and startup invocation therefore need disjoint evidence
classes:

1. `hol.ml` is an authenticated startup-input observation derived from an
   immutable inherited descriptor and the same exact child invocation;
2. the bootstrap loader ledger records its initial stock `loaded_files`
   snapshot count and ordered digest separately, requires original
   `strictbuild.hl` absent from that baseline, and then requires it in the
   post-observer delta; and
3. later action and post-action events remain stock ledger deltas, including
   the exact final-target/serializer suffix.

The later coverage adapter may include the authenticated `hol.ml` startup
input in the common selected logical closure, but it must derive that member
from the held startup capture rather than from a loader event.  Whether the
common closure includes or explicitly classifies that startup member must be
made exact before comparison; it cannot be left to a collector-local choice.

There is also a pre-ledger startup closure.  The pinned `hol.ml` immediately
loads generated `hol_loader.cmo`, later loads `pa_j.cmo`, and reaches topfind,
camlp5 archives and configuration through startup helpers.  In particular,
`hol_loader.cmo` implements the ledger whose output the request will observe.
Those OCaml bytecode/configuration reads are not necessarily HOL
`loaded_files` events or persistent `/proc/<pid>/maps` entries.  Exact
interpreter, bytecode, `hol.ml`, ELF-map and argv bindings therefore do not by
themselves authenticate the initial ledger implementation or its other
dynamically read inputs.

## Proposed repair

Because the existing closed artifact kinds already assign schema 3 to the
false combined interpretation, the conservative repair is a disjoint raw
schema/kind migration before production.  The migration must cover the plan,
request, transcript, native closure, complete and incomplete source
rederivations, disabled candidate identity, marker contract, capture envelope,
terminal capture completion, bundle and pair surfaces.  Retaining an old
`*-v1` capture kind while changing its closed key set would itself be schema
drift.  The existing versions must reject or remain categorically disabled;
they cannot accept the repaired shapes.

The proposed execution route is:

The adversarial boundary includes concurrent processes under the invoking host
uid; protecting only file bytes while leaving `ptrace`, `process_vm_writev`,
signals or the seccomp listener available to such a process would not close the
same race.  The supervisor must enter a private user/PID namespace as a
dedicated subordinate kernel uid, remain its non-dumpable root/tracer, and run
the child as a second dedicated subordinate kernel uid; neither uid may be
shared by another process.  The uid/gid maps, namespace inodes, credentials and
capabilities are closed receipt fields.  Negative startup
probes must show that an outside invoking-uid process cannot signal, ptrace,
process-vm-read/write, duplicate descriptors from, or enter the namespaces of
either process.  Yama policy alone is not authority.  A host without the
required subordinate ids and namespace isolation is unsupported.

1. Build a closed startup-artifact inventory before forking.  Every regular
   content-bearing member is copied through an already held descriptor into a
   distinct anonymous file created with `MFD_ALLOW_SEALING`, then fsynced,
   sealed with
   `F_SEAL_WRITE|F_SEAL_GROW|F_SEAL_SHRINK|F_SEAL_SEAL`, re-read and re-hashed.
   This includes the exact dynamic loader, `ocamlrun`, `ocaml-hol`, `hol.ml`,
   shared libraries, generated `hol_loader.cmo` and `pa_j.cmo`, findlib/camlp5
   archives and all configuration or package metadata that the closed startup
   contract permits.  The source pathname is only a selector used while
   preparing the inventory; the accepted identity is the sealed bytes.  The
   supervisor retains read-only descriptors for all sealed objects.  The child
   initially inherits only closed stdin/stdout/stderr endpoints, sealed
   bootstrap descriptors named by the contract, and the temporary seccomp
   listener slot described below.  Every descriptor number, flags, role,
   object digest and generation is explicit; no writable creator descriptor is
   inherited.
2. Before exec, the single child sets `PR_SET_NO_NEW_PRIVS`, installs a seccomp
   user-notification filter with `SECCOMP_FILTER_FLAG_NEW_LISTENER`, moves the
   listener to one contract-fixed close-on-exec descriptor, calls
   `PTRACE_TRACEME`, and raises `SIGSTOP`.  The already opened pidfd and exact
   PID/start ticks bind the child.  While it is stopped, the supervisor obtains
   the listener with `pidfd_getfd`, validates all inherited generations, and
   installs
   `PTRACE_O_TRACESYSGOOD|PTRACE_O_TRACEEXEC|PTRACE_O_TRACECLONE|PTRACE_O_TRACEFORK|PTRACE_O_TRACEVFORK|PTRACE_O_TRACEEXIT`.
   A clone, fork or vfork before the baseline is categorically forbidden; an
   event first places every resulting task in a traced stop and causes failure,
   so no task is allowed to run outside the single-task contract.
3. Avoid the kernel's otherwise implicit open of the `PT_INTERP` pathname.
   Require the inventoried dynamic loader to have no further `PT_INTERP`, copy
   it to a sealed executable memfd created with
   `MFD_ALLOW_SEALING|MFD_EXEC` (or a reviewed kernel-version equivalent), and
   invoke that exact descriptor with `execveat(AT_EMPTY_PATH)`.  Creation and
   an execution probe must reject a host `memfd_noexec` policy incompatible
   with this route.  Its exact argv directs it to the sealed
   `ocamlrun` descriptor, which receives exact procfd arguments for sealed
   `ocaml-hol` and sealed `-init` `hol.ml`.  These are the only procfd aliases
   and each fd generation and object digest is fixed.  There is no shebang-path
   exec and no unobserved kernel interpreter reopen.  The same-PID
   `PTRACE_EVENT_EXEC` stop must precede new image execution; at that stop the
   supervisor revalidates start ticks, exec event identity, canonical argv,
   cwd, sanitized environment and initial mappings.  Any platform on which the
   direct loader invocation or this pre-instruction stop cannot be established
   is unsupported rather than handled by a pathname fallback.
4. From filter installation through the baseline, every `open`, `openat` and
   `openat2` is a user notification.  While the only task is frozen, the
   supervisor reads a bounded pathname and interprets its dirfd generation,
   flags and logical role against the closed next-event contract.  It injects
   the corresponding supervisor-held sealed `O_RDONLY` object with
   `SECCOMP_IOCTL_NOTIF_ADDFD`, returns that exact child fd as the syscall
   result without `SECCOMP_USER_NOTIF_FLAG_CONTINUE`, and records the new fd
   generation.  Thus neither the pathname nor a hash before or after the open
   supplies byte authority: all child `read`/`pread`/`readv` and file-backed
   `mmap` operations consume the immutable injected object.  Unknown, extra,
   reordered, writable, truncating or non-inventory regular opens fail.  A
   notification ID is revalidated immediately before both injection and reply;
   a canceled or reused notification fails.
5. Directory lookup and metadata cannot silently steer the startup.  Directory
   fd generations are separate from regular-file generations.  Any permitted
   directory open, `getdents64`, `readlink`, `statx` or other namespace-result
   operation is either answered from the closed supervisor manifest while the
   task is stopped or its exact returned bytes are captured at syscall exit and
   matched to an expected bounded record before the child continues.  Relative
   lookup uses the recorded logical directory generation, never a later
   `/proc` pathname.  The implementation must prefer manifest emulation for
   directory enumeration; it may not trust a live directory and merely rehash
   it at the boundary.
6. Ptrace entry/exit accounting maintains a per-task (normally one-task)
   syscall state and a per-fd monotonically increasing generation across
   `close`, `dup*`, `fcntl(F_DUPFD*)` and exec.  Content ingress is closed:
   `read*`, `pread*`, `mmap*` and executable mappings are accepted only for a
   contract-known sealed fd generation or a separately classified immutable
   standard endpoint.  `open_by_handle_at`, `name_to_handle_at`, `io_uring*`,
   `SCM_RIGHTS`/`sendmsg`/`recvmsg`, sockets, pipes, `splice`/`tee`/`vmsplice`,
   `sendfile`, `copy_file_range`, child `pidfd_getfd`, `process_vm_*`, child
   `ptrace`, a second exec and every unclassified content-bearing mechanism are
   denied by seccomp and are fatal if observed.  File-backed `mmap` records the
   fd generation, offset, length and protections; anonymous memory is a
   separate non-ingress class.  `/proc/maps` remains an additional mapping
   observation, not byte authority.
7. The baseline endpoint is a supervisor-owned stdout pipe whose inode and fd
   generation are fixed before fork.  The marker must be the final bytes of
   one successful leader-task `write` or `writev`: the syscall-exit stop records
   exact TID/PID/start ticks, fd generation, pipe inode, requested length,
   returned length and the supervisor's cumulative stream offset, and the
   bytes drained from that exact interval must end in exactly one complete
   nonce-bound marker with no following byte in the same returned operation.
   Partial, duplicate, nonleader, wrong-offset or later pre-acceptance output
   fails.  Before accepting the boundary the supervisor holds an all-stop
   barrier, re-enumerates `/proc/<pid>/task` by start ticks, requires the single
   allowed task and no pending seccomp notification, and validates the ordered
   syscall/event digest.  Only then may startup tracing end.
8. The startup inventory, startup event stream, fd-generation table,
   namespace-result stream, baseline write and build provenance are separate
   versioned closed record kinds.  Each has an exact key set, canonical
   length-prefixed serialization, record-count and per-field byte caps, total
   byte caps, strict sequence numbers, a domain-separated ordered digest and a
   distinct-content digest; unknown keys, syscall classes or trailing data
   reject.  Inventory entries bind role, logical selector, object type, size,
   mode, SHA-256, permitted operations and build-receipt digest.  Open/access
   records bind task/start ticks, syscall and arguments, dirfd generation,
   result/errno, injected object digest, child fd generation and subsequent
   read/mmap use.  These schemas and their caps must be specified and reviewed
   before collector code exists.
9. Every generated CMO/CMA or other untracked build product has a closed build
   receipt from a fresh, initially empty isolated output directory.  It binds
   the source commit and tree/input digests, complete compiler/linker/runtime
   executable and library closure, tool versions and hashes, exact argv,
   sanitized environment, cwd, umask and locale, network-disabled execution,
   exit/wait status, stdout/stderr digests, and every output name, size and
   digest.  The artifact inventory points to that receipt and its sealed output
   bytes; a receipt copied from a different build, a dirty/prepopulated output
   directory, or an omitted tool/input/output is invalid.
10. After `hol.ml` startup and observer installation, emit in that baseline
   record the exact initial stock ledger count and ordered digest.  It must
   omit `strictbuild.hl`.  Load original `strictbuild.hl`, require its exact
   identity in a nonempty post-observer delta, and only then begin the 297
   action records.  A flattened bootstrap list is insufficient to establish
   this temporal boundary.
11. Keep later action and final-target/serializer records as genuine stock-
   ledger deltas.  Make coverage construction join the separately
   authenticated startup input with the ledger-derived closure under one exact
   rule that decides whether and how the startup member enters the common
   cross-runtime closure.
12. Update the deterministic request generator, immutable parser and all
   compatibility checks to the migrated contract before collector
   implementation.  The previously reviewed ten semantic payloads may retain
   their internal serialization rules, but their surrounding raw marker
   namespace and order contract must be migrated or explicitly proved
   independent of the retired native-startup interpretation.

An implementation must reject at least: a synthetic `hol.ml` ledger marker;
an unsealed, writable, aliased or wrong-child startup/bytecode fd; a live-file
open followed only by pre/post hashing; a notification continued into the
kernel rather than answered with the exact sealed object; a canceled/reused
notification; fd-generation confusion; shebang or implicit `PT_INTERP` path
execution instead of the sealed direct-loader route; mismatched exec, cmdline,
maps, cwd or environment; a missing/late/wrong-task exec or baseline stop; a
clone/fork/vfork, untraced task or absent all-stop barrier; `io_uring`,
`SCM_RIGHTS`, `open_by_handle_at` or any unclassified ingress; mutable or
unrecorded directory/metadata steering; a partial, wrong-inode, wrong-offset,
nonleader or nonsuffix boundary write; substituted, omitted, extra, mutable or
unreceipted startup CMO/CMA/configuration content; an open/event/build record
with unknown fields, exceeded caps, bad ordering or a mismatched digest; a
ledger implementation differing from the authenticated generated artifact;
missing, baseline-present or reordered original `strictbuild.hl`; alternate
`#use` or request-local startup; an unbound procfd exception; a startup capture
bound to another child; any legacy-kind/schema relabelling; and coverage that
drops, duplicates or relabels the startup member.

## First independent review

Independent review of exact clean commit `f5ffa1b8433718cd8f909434b9de6a2ebcb7ed50`
confirmed the factual diagnosis but rejected the first proposed repair.  Its
P1 finding was the mutable-name open race and omitted bytecode/interpreter
distinction.  Its P2 findings were incomplete migration closure and failure to
separate the initial ledger snapshot from the post-observer strictbuild delta.
Commit `c19272abd4d5289b0dd583e0fc959f1ef84f3ca1` incorporated those findings.
A second independent review confirmed their textual closure but found the
remaining pre-ledger artifact P1 and the missing post-exec/baseline
synchronization P2 described above.  Commit
`6df08a1663abcf803da85abb8f7daf6acc6ead47` incorporated that inventory and
trace proposal.  A third independent review rejected its remaining
hash-at-open/hash-at-boundary premise: a same-UID process could alter an
already opened live inode while the child read it and restore the accepted
bytes before the boundary.  It also required explicit task/syscall closure,
fd generations, a byte-exact boundary write, and closed startup/build schemas.
The present revision replaces live-file consumption with seccomp-notification
injection of sealed objects and incorporates those P2 requirements.  It again
requires fresh exact-commit review.

## Status

This is a blocking design audit, not an accepted repair.  It changes no
validator, generator or runtime and creates no candidate, coverage, approval,
PFT, S2, S3 or release evidence.  A hostile design review is required before
the schema boundary changes.
