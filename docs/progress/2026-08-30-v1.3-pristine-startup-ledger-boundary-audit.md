# Pristine startup versus loader-ledger boundary audit (2026-08-30)

## Finding

The accepted pristine raw protocol currently requires `candle:hol.ml` to be a
stock HOL Light `loaded_files` event before the original `strictbuild.hl`
event.  That requirement is not implementable by the planned pristine process
route.

In the pinned HOL Light source, `hol_loader.ml` initializes
`loaded_files = ref []`.  Only `load_on_path` appends a file identity after a
successful `use_file`; `loads` and `loadt` are wrappers around that function.
The top-level `hol.ml` is instead executed by OCaml's `-init` option before the
request source runs.  It loads its dependencies through `loads`, so those
dependencies can appear in `loaded_files`, but `hol.ml` never loads itself
through `load_on_path` and never appends its own identity.

This conflicts with the following current protocol facts:

- entrypoint step 0 starts pristine HOL Light from `candle:hol.ml`;
- step 1 installs the request-local native-ledger observer only after startup;
- `LOADER_LEDGER_POLICY` claims a stock `loaded_files` success ledger; and
- `validate_native_execution_closure` requires both `candle:hol.ml` and
  original `strictbuild.hl` in the bootstrap event slice, in that order.

The inspected inputs are content-fixed as follows:

- pinned `hol_loader.ml` SHA-256:
  `01d0f6b5a8ba557b58a352a464c25a408b80585a778d7cc61b11ea688290db29`;
- pinned `hol.ml` SHA-256:
  `9eabbd17397d942d116f1087e4b11d82746acc19ca77c11fed04046fdbec3e32`;
- reviewed pristine protocol SHA-256:
  `3c8fd6b5cfc2240a57ff45e3d1aa1592e3bb73f713101c975fa1dc4cd6f1fc84`;
- accepted semantic/capture design SHA-256:
  `e029cbf4b07e65865097a837fa7ec34dd297506548a3142583d4420b7be7a0e0`.

A generator could print a plan-bound `hol.ml` marker, but that would be a
synthetic startup claim, not a stock loader-ledger observation.  Relabelling it
as a native load would make the retained evidence internally well-shaped but
semantically false.  The step-4 request generator is therefore prohibited from
synthesizing this event, and no collector pilot is authorized under the
current closure contract.

## Evidence boundary affected

The startup source can still be authenticated, but by a different mechanism:
the future held collector must bind the exact child executable, argument
vector, working directory, environment, `-init` source path and bytes, and the
child/process identity that consumed the request.  The accepted capture
design's child-binding field list currently has detailed PID, wait, descriptor,
descendant and namespace facts but no closed executable/argv/startup-source
observation.  Relying only on the authenticated collector's source code would
leave this important execution fact implicit in the receipt.

The loader ledger and startup invocation therefore need disjoint evidence
classes:

1. `hol.ml` is an authenticated startup-input observation derived from the
   held child invocation and held source descriptor;
2. the bootstrap loader ledger begins with the actual stock `loaded_files`
   snapshot and must contain original `strictbuild.hl` after the observer is
   installed; and
3. later action and post-action events remain stock ledger deltas, including
   the exact final-target/serializer suffix.

The later coverage adapter may include the authenticated `hol.ml` startup
input in the common selected logical closure, but it must derive that member
from the held startup capture rather than from a loader event.  Whether the
common closure includes or explicitly classifies that startup member must be
made exact before comparison; it cannot be left to a collector-local choice.

## Proposed repair

Because the existing closed artifact kinds already assign schema 3 to the
false combined interpretation, the conservative repair is a disjoint raw
schema/kind migration before production:

- keep the already reviewed ten-line semantic payload grammar unless another
  finding requires changing it;
- move the plan, request, transcript, native closure and source rederivation to
  new schema/kind identities;
- change the native-closure policy and validator so the event list is only the
  actual stock ledger and rejects a synthetic `hol.ml` event;
- add a closed startup-invocation capture to the held capture envelope and
  terminal postflight, binding exact executable/argv/cwd/environment, held
  `hol.ml` identity and content, child identity, and request-source stdin;
- make coverage construction join the separately authenticated startup input
  with the ledger-derived closure under one exact reviewed rule; and
- update the deterministic request generator and parser compatibility checks
  to the migrated artifact contract before collector implementation.

An implementation must reject at least: a synthetic `hol.ml` ledger marker;
missing or reordered original `strictbuild.hl`; alternate `#use` or request-
local startup; changed `-init` path or bytes; relative/path-alias/symlink
startup arguments; executable/argv/cwd/environment drift; a startup capture
bound to another child; and coverage that drops, duplicates or relabels the
startup member.

## Status

This is a blocking design audit, not an accepted repair.  It changes no
validator, generator or runtime and creates no candidate, coverage, approval,
PFT, S2, S3 or release evidence.  A hostile design review is required before
the schema boundary changes.
