## Question and method

The proved fixed-polynomial hybrid reduced aggregate action-296 computation,
but its remaining cost had not been localized between polynomial blocks,
analytic operators, and evaluator entry.  A fresh run therefore replayed the
existing rational per-instruction profile and then applied the fixed hybrid to
the same eight accepted genuine subboxes in the same restored process.

For each backend and each box, all 54 top-level instructions were executed as
separate assumption-free `Kernel.compute` calls.  The resulting stack was
required to equal a one-shot execution of that backend, and the final result
was required to pass the certified checker.  Both backends passed 8/8 boxes
and 432/432 instruction steps without changing the axiom set.

## Reliable result

The one-shot whole-program comparison is meaningful:

| Eight separate box calls | Rational | Fixed hybrid | Speedup |
|---|---:|---:|---:|
| One-shot total | 20.6241 s | 8.6565 s | **2.38x** |
| Average per box | 2.5780 s | 1.0821 s | **2.38x** |

This independently confirms the fixed backend's benefit on genuine complete
programs.  The factor is lower than the established 9.14x eight-box internal
batch because these are eight separate calls rather than one aggregate call.

The matched empty-value controls expose that distinction:

| 432 calls with the backend equation table | Total | Per call |
|---|---:|---:|
| Rational | 18.2404 s | 42.22 ms |
| Fixed hybrid | 26.7960 s | 62.03 ms |

The fixed equation set therefore has about 1.47x the fixed per-call cost in
this experiment.  That cost is paid 432 times by the instruction profiler but
only once by the production internal batch.

## Why opcode timings are not an attribution

The raw time inside the 432 instruction markers was 55.4614 seconds rational
and 58.2391 seconds fixed.  Several fallback `sqrt`, `atn`, and `add` markers
look slower in the fixed run, while the two large polynomial blocks are
faster.  Those values cannot be interpreted as an execution-time breakdown:

- each marker contains a complete `Kernel.compute` entry, equation checking,
  function-table construction, input translation, and result conversion;
- the larger fixed equation table makes that boundary backend-dependent;
- a constant-call subtraction is not valid for large, differently shaped
  inputs; and
- the stepwise rational profile additionally scans and prints every complete
  intermediate result outside the markers, while the fixed profile does not.

This is a useful negative result.  Repeated external calls are suitable for
exact intermediate-result debugging, but not for deciding whether to optimize
square root, inverse, arctangent, or dense Taylor composition.

## Next discriminator

The next useful profile must keep the evaluator boundary coarse.  A bounded
experiment should capture authentic intermediate operands during untrusted
preparation, partition the real steps into fixed-polynomial and rational
fallback jobs, and validate each partition in one internal computed batch
returning a compact verdict.  That preserves real data shapes while paying
equation validation and result conversion once per partition.

Only after that aggregate measurement should another arithmetic backend or
operator-specific proof be started.  Production should continue to use one
computed verdict; this experiment gives no reason to replace the completed
general analytic soundness or exact tree proof.
